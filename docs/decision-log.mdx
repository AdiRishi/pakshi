## 046 — Someone typing in a replaced field is told when they stop [#decision-046]

**Context.** The later write to a field wins, and its earlier writer is told. When two people type in one field, each batch replaces the other person's, several times a second. A notice for each would be noise, but staying quiet while someone types left whoever stopped second never knowing they'd lost.

**Decision.** A person whose write is replaced is told at once, unless they have an unconfirmed write to that field, which will replace it in turn. Only writes made since they opened the editor count: `SiteDoc` remembers every writer, but a change to something they wrote on an earlier visit isn't news to them. If they're still typing in the field, the notice waits until they stop, and is dropped if they type over the replacement, because then the other person is told.

**Consequences.** Whoever ends up replaced hears it once. The typing marker in presence remains the way people avoid typing in one field together.

## 045 — Remote changes wait for composition, and the canvas keeps the view in place [#decision-045]

**Context.** The editor spec's rules say nothing is written into a field while an input method composes, and the change applies when composition ends. A field's value is replaced whole, so applying the stored value then would drop what was composed, and saving the composed value would drop the change. The rules also say the view stays put when content grows above it. Chrome anchors scrolling on its own and Safari doesn't, so a test in Chrome passed without the editor doing anything.

**Decision.** During composition a field saves nothing and takes no remote change. When it ends, a change that arrived meanwhile is made again around what was composed: in plain text by moving the composed splice onto the new value, in rich text by mapping the change's steps through the composition's own. The result is saved as the person's edit. The canvas turns the browser's scroll anchoring off, and before each remote change notes the focused element or the first field or block in view, then scrolls by however far it moved. Settings panel text inputs are uncontrolled, like the canvas's fields, so a remote change keeps their caret too.

**Consequences.** Every browser behaves the same, and each rule has a browser test that fails without it.

## 044 — Studio forwards live connections before TanStack Start [#decision-044]

**Context.** The design passes Studio's WebSocket to `studio-api` over the service binding, which Cloudflare doesn't document. TanStack Start's request handling serves pages and server functions, and runs its responses through its own middleware.

**Decision.** Studio's server entry, `apps/studio/src/server.ts`, sends `/api/live/{site}` to `studio-api` unchanged, before TanStack Start sees it. `studio-api` refuses a connection from another origin, checks the session and `page.edit`, and passes the socket to the site's `SiteDoc` with the person and their permissions in a header it sets itself, replacing any the browser sent.

**Consequences.** The passthrough works in the dev stack's local runtime, from the browser through both Workers to `SiteDoc`. The agent's chat panel in checkpoint 7 can take the same route.

## 043 — Live connections catch up from the batch log [#decision-043]

**Context.** [Decision 032](#decision-032) sent one batch at a time over RPC until live co-editing. A live connection drops and comes back, and the editor must neither miss a batch nor apply one twice.

**Decision.** The editor still opens a draft from Studio RPC. Every connection then starts with Sync and the editor's revision, and `SiteDoc` answers with the batches committed since, from its batch log, or with the whole draft when the editor is more than 500 batches behind. The editor sends every batch `SiteDoc` hasn't confirmed, in order, without waiting on each, and sends them again on each new connection; `SiteDoc` answers a batch it already committed with Known. Broadcasts carry revisions, so the editor skips one it has and asks for a sync after a gap. `SiteDoc` handles live messages and commits one at a time, so each commit's broadcast leaves before the next commit. Studio's page list still commits over RPC, and `SiteDoc` broadcasts those commits too.

**Rejected.** Sending the whole draft on every connection, which grows with the site; letting PartySocket buffer messages while closed, which would send them a second time after the editor's own resend.

**Consequences.** A property test with three editors making random edits, undos and reconnects ends with every editor showing `SiteDoc`'s draft.

## 042 — Undo passes over parts someone else wrote since [#decision-042]

**Context.** [Decision 033](#decision-033) left the undo rule for live co-editing: an undo applies only where its author's write is still the latest. `SiteDoc` has to know that for every field and block an undo touches, including after it restarts.

**Decision.** `SiteDoc` keeps the latest writer of each part of a draft in a `writes` table, written in the same transaction as the batch. A part is a field or a part of one, a block's variant, surface or place, a whole block with its items, or a page's meta field, address or whole page. A write replaces the records below its part. An undo batch is marked as one, and `SiteDoc` applies each of its ops whose part is still its author's latest and still exists, and passes over the rest. Redo goes the same way. The broadcast carries the ops that applied, the positions of those passed over, and the people whose writes a value change replaced, who are told. The rule is the document module's `commitBatch`, which the editor's tests run too.

**Consequences.** Undo never erases someone else's change, and says what it left. The table grows with the parts of a draft, not with its history.

## 041 — Permission changes reach live connections with the permissions screens [#decision-041]

**Context.** Checkpoint 4 asked that removing a person's permission stop their next batch. Nothing changes a grant until the permissions screens in checkpoint 10, so the code that tells `SiteDoc` about a change would have no caller.

**Decision.** `studio-api` finds the person's permissions on the site when it opens their live connection. `SiteDoc` keeps them on the connection and checks every batch against them, with no D1 read. Checkpoint 10's grant and override changes tell the `SiteDoc`s they affect to reload them, and its checks include a removed permission stopping the next batch.

**Consequences.** Until checkpoint 10, a permission removed while someone is connected lasts until their connection reopens.

## 040 — Dragging is for pointers; the keyboard moves blocks with commands [#decision-040]

**Context.** The editor spec lists keyboard dragging as dnd-kit's job and names "dropping the keyboard" as a mistake Puck made. dnd-kit 0.5's keyboard sensor moves a plain draggable 10 pixels per arrow press, and its accessibility plugin announces raw IDs and puts its description element in Studio's document, where a handle inside the canvas can't reference it. Meanwhile, move up, move down and move to already reach every spot a drag can, from the keyboard, the outline and the block menu.

**Decision.** Drag handles take the pointer sensor only, with a 4-pixel distance so a click stays a click. They are hidden from assistive technology and left out of the tab order. The keyboard moves blocks with the move commands, and each move is announced with where the block landed. A drop runs the `place` command, whose moveBlock comes from the same `moveOp` the move commands use.

**Rejected.** dnd-kit's keyboard sensor with a plugin that jumps between drop spots, which would be a second keyboard path to the same moves; dnd-kit's accessibility plugin.

**Consequences.** Puck's mistake was offering no keyboard path at all. Here every drag has a command, as WCAG 2.5.7 asks, and a drag and the matching command produce the same ops.

## 039 — The picker previews one block, and layouts are chosen from the block's own content [#decision-039]

**Context.** The editor spec asked for a thumbnail per block in the picker, rendered from a fixture, and for variants and surfaces chosen from previews. A thumbnail small enough for a grid of a dozen blocks can't be read, and each rendered thumbnail is a frame of its own.

**Decision.** The picker lists blocks by name, with search, and previews the highlighted one in the draft's theme with the placeholder content it will start with. The settings panel renders the selected block's own content in each of its layouts, and shows each background as a swatch of the theme's colors for that surface. Layout previews follow the block's content once typing pauses, so a keystroke never renders them.

**Consequences.** A person sees exactly what they'll get before choosing. The picker renders one preview frame, and the settings panel one per layout.

## 038 — Items move up and down across sections [#decision-038]

**Context.** The editor spec listed four move commands: up, down, into the previous section, and out to the top level. Placement rules make the last two impossible: items go only in a slot that accepts them, and sections only at the top level.

**Decision.** Move up and move down move a block one place in its list. An item at either end of its slot moves into the nearest slot before or after it that accepts it, even in another section. Move to puts an item at the end of any other slot that accepts it. The header and footer belong to every page, so they don't move.

**Consequences.** A keyboard user can take an item anywhere it's allowed with two commands, and no command is ever offered that placement rules would refuse.

## 037 — A placeholder is a block's own starting content, found by its value [#decision-037]

**Context.** The editor spec gives every block placeholder content for a new instance, and pre-flight blocks a submission while any placeholder remains, but nothing defined what a placeholder is. An empty required field can't be one: a draft always holds required fields, and an image, a form or a link has no empty value. A new block should also look finished, not like a form waiting to be filled in.

**Decision.** Every section and item version ships a `fixtures/placeholder.json`, which `defineBlock` decodes into its contract. It uses built-in images and a contact form that every site resolves through `siteData`. `placeholderPaths` finds the fields still holding placeholder content: a built-in image or form, a button whose link is unchanged, or text, rich text or a link equal to a placeholder of that block type, including the items in a section's placeholder. A button's label alone doesn't count, because short labels such as "Get started" are often real.

**Rejected.** Empty required fields as placeholders, which would let drafts lack required values; a marker in the document, which every op, undo and merge would have to carry.

**Consequences.** The document gains no field, and a placeholder stops being one the moment its value changes. The placeholder is a fixture, so the screenshot and axe gates cover it. When the agent lacks content ([decision 026](#decision-026)), it can leave a block's placeholder values in place, and pre-flight finds them the same way.

## 036 — The canvas fixes the theme's color scheme instead of following the system [#decision-036]

**Context.** Sites follow the visitor's color scheme through `prefers-color-scheme`, and the editor lets a person switch the canvas between light and dark. The editor spec asked for the frame's `color-scheme` to do this, but a frame's `prefers-color-scheme` follows the operating system in Chromium, not the frame element's `color-scheme`.

**Decision.** `themeCss` takes an optional scheme. Without one it writes both schemes behind the media query, as sites need; with one it writes only that scheme's variables. The canvas passes the scheme the person chose.

**Consequences.** Both schemes of a theme render from the same variables in both places, and the canvas-versus-sites screenshot checks compare them in each scheme.

## 035 — Tailwind's spacing scale counts as a theme token in blocks [#decision-035]

**Context.** Blocks may use theme tokens only, and a lint rule rejects "literal colors, fonts or spacing". Read strictly, that forbids `gap-6`, and blocks couldn't lay themselves out. But `--spacing` comes from the theme's density, so every step of Tailwind's spacing scale already moves with the theme.

**Decision.** `pakshi/no-literal-styles` rejects arbitrary values for colors, fonts and spacing, Tailwind's own palette colors, font families other than the theme's, and inline styles. It allows the spacing scale and layout utilities such as aspect ratios. Which classes bypass the theme is decided in `@repo/tokens`.

**Consequences.** A block can't hard-code a look, and a density change still respaces every block.

## 034 — Islands and media upload wait for the checkpoints that need them [#decision-034]

**Context.** Checkpoint 2 adds a gallery and a form block, and the editor spec's media popover offers uploads. No checkpoint builds Astro's island map, a form posts as plain HTML without it, and uploads belong with the media library and Cloudflare Images in checkpoint 9.

**Decision.** Gallery v1 is a static grid with no lightbox, and the form block renders a plain HTML form through a shared `FormView` component, so how forms post can change without a new block version. The media popover chooses from the site's and brand's libraries and edits alt text; uploading arrives with the media library.

**Consequences.** Nothing hydrates on sites yet. The first interactive block builds the island map, and a lightbox arrives as a new gallery version.

## 033 — A draft's history is its batch log until something reads more [#decision-033]

**Context.** The technical design records one revision per editing session or agent turn, with a full checkpoint every so often. Nothing reads them before the audit log, restore and agent-turn undo, and SiteDoc needs a record of committed batches anyway, to apply a batch sent twice only once.

**Decision.** SiteDoc stores every committed batch with its actor, time, revision, ops and inverse ops. Grouping into sessions and full checkpoints wait until a feature reads them. Undo sends a command's inverse ops as an ordinary batch; the rule that skips fields someone else changed since arrives with live co-editing, which has the test for it.

**Consequences.** Sessions and turns can be derived from the log later without a migration.

## 032 — The editor sends batches over RPC until live co-editing [#decision-032]

**Context.** Checkpoint 4 connects Studio to SiteDoc over PartySocket. Checkpoint 2 has one person editing, so the WebSocket's broadcast and presence have nothing to do yet.

**Decision.** The editor sends batches through a `Connection` with one method, `send`. Studio implements it with the `applyBatch` server function, which calls `StudioRpcs.applyBatch`, and studio-api calls the site's SiteDoc. The editor sends one batch at a time and resends one that didn't arrive with the same ID.

**Consequences.** Each batch checks the session and reads the person's grants from D1, which the WebSocket's per-connection permission cache replaces in checkpoint 4. Only the `Connection` implementation changes then.

## 031 — Ops name their page, and cover variants, surfaces and addresses [#decision-031]

**Context.** The op vocabulary addressed a block by ID alone, but each draft page is its own SQLite row, so SiteDoc would need an index from block to page. The editor also needs to change a block's variant and surface, and renaming a page can change its address, and no op did either.

**Decision.** Block ops name their target: a page, or `site` for the header and footer. Structure ops name their page. `setVariant`, `setSurface` and `setPath` join the vocabulary, and `setPath` refuses an address another page has.

**Consequences.** An op touches exactly one row, and merging, undo and the agent use the same ops.

## 030 — Alt text belongs to where an image is placed [#decision-030]

**Context.** The snapshot manifest stored alt text on the media file, and the media popover edits it. Editing a shared library record would change every draft at once, outside any draft or approval. Alt text also depends on context: the same photo can say something in one place and be decoration in another, which pre-flight's check for alt text on every meaningful image needs to know.

**Decision.** A media reference in props carries its own `alt`. An empty alt marks an image as decorative; a missing one is incomplete, which freezing checks. The library keeps an alt text per image only as the suggestion for new placements.

**Consequences.** Alt text changes through drafts and approvals like any other content, and merges field by field.

## 029 — Studio calls studio-api through an Effect RPC contract [#decision-029]

**Context.** Studio called a method on `studio-api`'s entrypoint class over native Workers RPC. The contract was that class's TypeScript type, so nothing checked calls at runtime, failures reached Studio untyped with no timeout, and every method took the session cookie as an argument. `studio-api` must stay a plain Worker, because PartyServer and `AIChatAgent` need plain Durable Object classes, so Alchemy's Effect Worker RPC doesn't apply.

**Decision.** Each API boundary is an Effect `RpcGroup` in `packages/contracts`, with payload, success and error schemas for every method. `studio-api` serves `StudioRpcs` from a named `StudioRpc` entrypoint, over Effect RPC's HTTP protocol. Studio calls it through one helper that sends the session cookie and Studio's origin as headers, applies a timeout, stops when the browser request is cancelled, and turns every failure into a user-safe error in one place. A `StudioSession` middleware on the contract checks the session and provides the signed-in person to handlers; a missing session is the typed `Unauthenticated` error. Sign-in stays plain HTTP over the default entrypoint.

**Rejected.** Native Workers RPC with a TypeScript interface, which has no runtime checks or typed errors; Alchemy's Effect Worker class, which can't host PartyServer's Durable Objects.

**Consequences.** A new Studio feature adds one `Rpc.make` to the contract and one handler, and gets validation, the session check, the timeout and error mapping with it. Each call pays for JSON encoding and an internal HTTP hop, and the transport uses `effect/unstable/rpc`, which may change before Effect 4 is released.

## 028 — Two stacks, dev and prod, and destroying one deletes everything [#decision-028]

**Context.** The design had branch, staging and production stages, retained production's D1 databases and R2 buckets on removal, and failed CI on any production plan that deleted a database, a bucket or a Durable Object class. That meant another account to run, and teardown that left data behind.

**Decision.** Pakshi has two stacks: `dev`, which runs locally, and `prod`. `dev:destroy` and `prod:destroy` delete everything in the stack, Durable Object data and the R2 bucket's contents included. Test suites deploy throwaway local stages. Checks that need Cloudflare's network run against production.

**Rejected.** A staging stage; retaining production stores on removal; a CI check on the production plan.

**Consequences.** Nothing stands between a destroy, a removed resource or a renamed Durable Object binding and production data. Recovery relies on D1 Time Travel and Durable Object point-in-time recovery within their 30-day windows, and a destroyed stack can't be recovered that way.

## 027 — Serve sites through Alchemy's Astro adapter, with lookup and cache in middleware [#decision-027]

**Context.** The design named `@astrojs/cloudflare`. Alchemy's `Website.Astro` resource, which builds, emulates and deploys the `sites` Worker, adds its own fork of that adapter, fails the build if the app declares one, and owns the Worker's entry file. `sites` has to look up the host and release in KV and serve pages from the Workers Cache API before Astro renders.

**Decision.** `sites` uses Alchemy's Astro resource and adapter. The host → site → release lookup, the page cache and media serving run in Astro middleware, which sees every request after static assets. The cache key is the release ID, the Worker version and the path, as before.

**Rejected.** Building with the upstream adapter and deploying the output as a plain Worker, which gives up Alchemy's local emulation and build memoization for `sites`; a separate front Worker for caching, which adds a fifth Worker; Cloudflare's newer Workers Caching and Astro 7's route cache built on it, whose cache key leaves out the hostname, so one Worker serving many sites would need a gateway Worker to tell them apart, and Alchemy's adapter turns Astro's cache provider off.

**Consequences.** `sites` has no Worker entry of its own, so anything that must run before Astro goes in middleware. The Cache API does nothing on `workers.dev` hostnames, so deployed pages are cached only once `sites` serves a custom domain; the dev stack emulates the cache locally. The key starts with the site, and only GET and HEAD requests use the cache.

## 026 — Drafts may be incomplete; completeness is checked at submission [#decision-026]

**Context.** `SiteDoc` validated every batch against the full block schema. A heading with a 3-character minimum could then never be cleared to retype it, and a person couldn't leave a required field empty while working on the rest of a page.

**Decision.** People's batches are checked for types, integrity, link rules and the limits the editor enforces while typing: maximum lengths, allowed marks and nodes, variants and surfaces. Completeness (required fields and minimum lengths) is checked when a draft is frozen, and pre-flight lists what's missing. The agent's batches are also checked for completeness, so it gets a structured error instead of leaving a field empty; where it lacks content it writes a placeholder, which pre-flight also blocks.

**Rejected.** Full validation on every batch, which blocks ordinary editing; keeping a separate unsaved value in the editor until a field is valid, which is a second copy of the page that other people and the agent can't see.

**Consequences.** A draft can hold incomplete blocks, and the editor marks them. Nothing incomplete can be submitted or published, because freezing checks the full contract.

## 025 — Build our own visual editor on the page document, instead of Puck [#decision-025]

**Context.** [Decision 013](#decision-013) kept Puck and added a sync module. That meant a two-way adapter to Puck's tree, converting Puck's HTML rich text to TipTap JSON, translating our ID-based ops into Puck's index-based actions, taking over its undo, and working around seven known gaps, with a full reload when a client fell out of step. All of it existed because Puck keeps its own copy of the page. A source review of Puck 0.23 found 23,769 lines of TypeScript, about 5,400 of them for drag and drop into arbitrarily nested zones, which Pakshi's two-level documents don't need. It also found no collaboration support, and focused fields that overwrite remote changes. EmDash and Payload have no on-page structure editing or live collaboration to adopt instead.

**Options.** (a) Puck with a sync module ([013](#decision-013)). (b) A fork of Puck. (c) Our own editor on our page document, using TipTap for rich text fields, dnd-kit for drag and drop, and shadcn/ui for controls. (d) A ProseMirror document for the whole page, with sections as nodes.

**Decision.** (c). `@repo/editor` in `packages/editor`, specified on the [Editor](/editor) page. It renders the page into a same-origin iframe with the same components and CSS as `sites`, and it keeps a local copy of the draft in step with `SiteDoc` by running the same document module. Blocks render their fields through field components from `packages/blocks`, which output plain markup on the site and editable markup in the editor. The editor also needs four changes elsewhere:

- `applyOps`, validation and inverse ops form a document module in `packages/domain` that imports no server code, so the browser can run it.
- Batches, new blocks and new list items carry IDs their sender creates, so a batch sent twice has no extra effect.
- Lists inside props carry item IDs, and paths address items by ID.
- Undo is per command: an undo batch applies only to fields where its author's write is still the latest.

**Rejected.** (a), because the sync module and its gap handling were the riskiest work in Pakshi and would remain a second copy of the page to reconcile. (b), because we would own a 24,000-line codebase built around index addressing. (d), because ProseMirror addresses content by position and its collaboration model needs a server that rejects stale versions, so we'd need the adapter again, and `SiteDoc` orders batches with last-write-wins per field instead. Dragging blocks from a palette into the canvas, because a "+" at each insertion point does the same job without cross-frame dragging.

**Consequences.** No adapter, no rich text conversion and no reload to recover from drift. We own the canvas, overlays, drag-and-drop behaviour and keyboard support, and the [build plan](/build-plan#2-editing-content) gives the editor two checkpoints before live co-editing. The field components become part of every frozen block version, so their contract must stay small and stable.

## 024 — The site's Durable Object owns approvals and publishing [#decision-024]

**Context.** Approval progress lived in D1 while the snapshot being approved, merges and the live release lived in `SiteDoc`. An approver could act on a stale D1 view after a merge had restarted the workflow, and two final approvals could both pass the "based on the current live release" check while `SiteDoc` waited on R2.

**Decision.** `SiteDoc` owns submissions and their approval progress, and D1 keeps a copy for dashboards. An approval decision goes to `SiteDoc`, which rejects it if the submission changed since the approver loaded it. Publishing checks approval and the live release again after its last R2 write, then records the new live release. `SiteDoc` is the only writer of the live release to KV; the reconcile job asks it to rewrite and never writes KV itself.

**Consequences.** Approvals, restarts, publishes and rollbacks for a site happen in one order, in one place. The Approvals screen reads a copy that can lag by seconds, but a decision based on it can't take effect if it's stale.

## 023 — One-click rollback undoes only the latest publish [#decision-023]

**Context.** Rolling back to any past release without approval could bring back content that was removed on purpose, such as a page pulled for legal reasons.

**Decision.** One-click rollback, with no approval, undoes the most recent publish and can't be repeated to walk further back. Any older release is restored as a draft, which goes through the site's workflow like any other change.

**Rejected.** Rollback to any release without approval.

**Consequences.** A bad publish is still undone in about a minute. Older content returns only with approval.

## 022 — Each site's submissions in their own Durable Object [#decision-022]

**Context.** One shared D1 `submissions` database, capped at 10 GB, would let a flood on one site's form fill it and break forms on every site. D1 databases can be created through the API, but a Worker reaches D1 only through bindings fixed at deploy time, about 5,000 per Worker, so a database per site would mean a redeploy for every new site or querying through the account API and its rate limit ([D1 limits](https://developers.cloudflare.com/d1/platform/limits/)).

**Decision.** Each site's submissions live in a `SiteSubmissions` Durable Object with SQLite storage, hosted by `sites-api` and bound from `studio-api` for authorized reads. The site's first form post creates it. Form posts over 64 KB are rejected.

**Rejected.** One shared D1 database; a D1 database per site.

**Consequences.** Each site's customer data is isolated, with up to 10 GB and 30-day point-in-time recovery per site, and no provisioning. Nothing can query submissions across sites, which the product doesn't need.

## 021 — No spam protection on forms [#decision-021]

**Context.** The design gave every site its own Turnstile widget, but non-Enterprise accounts are limited to 20 widgets ([plans](https://developers.cloudflare.com/turnstile/plans/)). Honeypots and rate limits add setup and edge cases for little early value.

**Decision.** Forms ship without spam protection. To keep an unprotected form from sending mail to any address a visitor types, forms send no email to submitters; notifications go only to the form's configured addresses.

**Consequences.** Spam can reach a site's submissions until protection is added, but only that site's ([022](#decision-022)). When it is, one widget covers the sites domain and its subdomains, and custom domains are grouped 10 to a widget.

## 020 — Share drafts like documents [#decision-020]

**Context.** People need to show drafts to colleagues and to people outside the organization, and to invite others to edit.

**Decision.** Drafts are shared like documents: with named people, the whole organization, or anyone with the link, and the person sharing chooses view or edit access for each. Every draft has a preview link at an address that can't be guessed, served from a fixed R2 key that each save overwrites; KV is too slow to show the latest save. Editing always needs a signed-in Pakshi user, so a link shared for editing gives everyone else view access. Edit access through a share covers one draft and never includes submitting or publishing.

**Rejected.** Previews visible to signed-in staff only; frozen previews with fixed expiry times.

**Consequences.** A preview lives as long as its draft and always shows its latest saved state. Approvers still review a frozen submission snapshot.

## 019 — Brand changes reach sites as drafts; no brand locks [#decision-019]

**Context.** A brand theme change would otherwise ship with whatever unrelated change a site publishes next. Brand locks, which limit what sites may change, add a validator, hidden controls and agent rules.

**Decision.** Sites use their brand's theme and identity as they are, with no overrides and no locks. Each save of a brand's theme, logo or favicon is an immutable brand revision, and each draft pins one, the way its lockfile pins block versions. A new revision creates a Brand update draft on every site in the brand, or moves an unpublished one forward, and it follows that site's workflow. Other drafts keep their pinned revision until they merge after the update is live. The same mechanism creates block upgrade drafts on every affected site.

**Rejected.** Brand locks and site theme overrides; theme changes that ride along with the next publish.

**Consequences.** A site that needs a different look belongs to a different brand. Locks can be added later if a real need appears.

## 018 — Media files never change [#decision-018]

**Context.** Replacing a file everywhere it's used would change live sites without a publish.

**Decision.** Each upload is a new file with its own ID, and files are never replaced or versioned. A new image appears only where someone swaps it in. The brand logo and favicon are brand settings that point at a file, so changing them reaches sites through Brand update drafts ([019](#decision-019)). A file is kept while any draft or live release uses it, and for 3 months after the last one stops.

**Consequences.** A media ID always renders the same file. Changing a common asset other than the logo or favicon means updating each place it's used.

## 017 — Named drafts that merge like branches [#decision-017]

**Context.** With one shared draft per site, one person's unfinished page blocks another person's urgent fix or ships with it, and a second submission replaces the first.

**Decision.** A site has one live release and any number of named drafts, each starting from a release. Publishing a draft makes it live, and every other draft is then behind. A draft that's behind must be updated the next time it's opened and before it's submitted. Updating is a three-way merge by block ID and field. Different fields, blocks or pages merge automatically; conflicts (same field on both sides, edit against removal, the same list reordered on both sides) need a person, and a model may suggest a merge for text. A submission under review that merges cleanly keeps its approvals; one that needed a person restarts its workflow.

Five rules keep merges safe. All sides are migrated to the newest block version any of them uses before diffing. The merged draft is checked for structure, and a failure is a conflict; pre-flight runs only at submission. A submission publishes only if it's based on the current live release. Publishing closes a draft only if nobody edited it after it was submitted. And people already in a draft that falls behind keep working; the update is required the next time it's opened and before it's submitted.

**Rejected.** One draft per site; publishing chosen pages from a shared draft; a draft per page.

**Consequences.** More to build: a drafts list, the merge engine and a conflict screen. The [build plan](/build-plan#5-publishing-and-merging) proves the merge engine early. Several people can still edit one draft live together ([007](#decision-007)).

## 016 — Keep all site data [#decision-016]

**Context.** Form submissions and past releases are part of a site's data.

**Decision.** Nothing deletes submissions or releases automatically. They are kept for as long as the site exists. A single submission, or everything for one person, can be deleted on request.

**Consequences.** Storage grows over time, which Durable Objects and R2 handle comfortably. An earlier release can come back while its block versions and media are still retained ([006](#decision-006), [018](#decision-018), [023](#decision-023)).

## 015 — Approval workflows on the organization, a brand or a site [#decision-015]

**Context.** Review requirements differ between sites and brands, and the people who own a site know them best.

**Decision.** Workflows can be set on the organization, a brand or a site, and the nearest one applies. A workflow is an ordered list of any number of steps, including none, each naming who can approve (roles or people) and how many approvals it needs. Definitions are rows in D1, and each submission's progress lives in the site's `SiteDoc` ([024](#decision-024)); completing the last step publishes. The workflow editor is a list of steps. A visual, node-based editor built with an off-the-shelf flow library can follow, on the same definitions.

**Rejected.** A fixed cap on approval steps; a general-purpose workflow engine.

**Consequences.** Owners at each level control their own review process without platform changes. Editing a workflow is a permission, so whoever holds it controls how a site publishes.

## 014 — Fine-grained permissions, with roles as bundles and per-person overrides [#decision-014]

**Context.** Brands are just groupings of sites; what people may do must be controlled precisely and the same way everywhere.

**Decision.** Permissions are fine-grained named actions, and they decide what a person can do. Roles are sets of permissions for giving access quickly, with defaults shipped by Pakshi and custom roles created by admins. Grants give a person a role on the organization, a brand or a site, and inherit downward. An override switches one permission on or off for one person on one scope and beats any role. A person can grant only permissions they hold, on scopes they control. One `authorize` function in `packages/domain` is used by the API, the agent's tools, live editing and Studio's UI.

**Consequences.** One place to reason about access. New features add permissions rather than new checks. Rules such as self-approval are permissions, so admins decide them.

## 013 — Integrate Puck through a sync module; don't fork [#decision-013]

**Superseded** by [decision 025](#decision-025): Pakshi builds its own editor.

**Context.** Live collaboration needs Puck to accept changes from others without losing the user's place or undo. Puck has no collaboration support. Its core is about 24,000 lines of TypeScript under the MIT license, built on a zustand store with a reducer of small actions ([source](https://github.com/puckeditor/puck)).

**Options.** (a) Fork Puck. (b) A sync module on Puck's public API, plus patches where the API falls short. (c) Build our own editor.

**Decision.** (b). Puck already exposes what the sync needs: an `onAction` callback for every local change, small actions (insert, move, remove, replace) we can dispatch for remote changes, a flag to keep them out of its history, and lookup by block ID. Puck's actions address blocks by index, so the sync module converts our ID-based ops using that lookup. The biggest gap is undo, which restores whole-page snapshots, erasing other people's changes, and has hard-wired shortcuts. We take the undo shortcuts in capture-phase key listeners and hide Puck's undo buttons, so no patch should be needed; if that proves not to be enough, a pnpm patch replaces its history slice. Smaller gaps, such as fresh IDs on replayed inserts, index-based selection and focused fields that ignore remote changes, are handled in the sync module and proven in the [build plan](/build-plan#4-live-co-editing).

**Rejected.** A fork: we would own drag and drop, the canvas iframe and every field type, and fall behind an actively developed 0.x library. Our own editor: much larger, for no gain.

**Consequences.** We keep Puck's upgrades, and re-check the patch on each one. If the [live co-editing checkpoint](/build-plan#4-live-co-editing) shows the public API can't support live editing well, we revisit a fork with evidence.

## 012 — Effect Schema instead of Zod [#decision-012]

**Context.** The starter defines shared schemas with Effect Schema (Effect v4). The earlier design assumed Zod 4.

**Decision.** Use Effect Schema as the one schema library for pages, blocks, edit operations and agent tools. It produces Standard Schema and JSON Schema, which cover editor control generation and agent tool definitions.

**Consequences.** One schema library and one style across the repo. Libraries that expect Zod specifically (for example some json-render helpers) are used only through JSON Schema, or not at all.

## 011 — Build on application-platform-starter [#decision-011]

**Context.** A starter already exists with a monorepo pattern and utilities for Cloudflare apps ([repo](https://github.com/AdiRishi/application-platform-starter)).

**Decision.** Pakshi starts from it: pnpm and Turborepo, Alchemy for all infrastructure and bindings (instead of Wrangler configs), Effect for application services, oxlint and oxfmt with its lint rules, TypeScript 7, Vitest, Playwright, and Blume docs with repository ADRs. Its `apps/web` becomes `apps/studio`, and `apps/sites` is added for Astro.

**Consequences.** A working foundation from day one. Alchemy is a beta dependency pinned (with a patch) by the starter, so upgrades are deliberate. PartyServer and `AIChatAgent` Durable Objects are plain classes, which a starter-style Effect Worker can't host, so `studio-api` is a plain Worker with its own entry file. Alchemy deletes a Durable Object class's data when the class leaves a Worker, so CI fails if a production plan removes one.

## 010 — Workers Paid plan; no Enterprise features, no root domains [#decision-010]

**Context.** Pakshi should not need a Cloudflare Enterprise subscription.

**Decision.** Run production on the Workers Paid plan (from $5 a month per account plus usage). The Free plan's 10 ms CPU per request, 100,000 requests a day and missing Email Service sending rule it out for production. The only Enterprise-only feature in the earlier design, apex proxying for root domains, is dropped: sites use subdomains such as www, and owners redirect the root domain at their DNS provider.

**Consequences.** Predictable, low cost. Any future feature that needs Enterprise must be raised as a new decision.

## 009 — Staff sign-in with Better Auth over OIDC, not Cloudflare Access [#decision-009]

**Context.** Staff need SSO with the organization's identity provider. Cloudflare Access works at the network edge, which limits how much control Studio has over the sign-in experience and sessions.

**Decision.** Run our own auth with Better Auth in `studio-api`. Its `genericOAuth` plugin connects to the organization's one identity provider over OIDC, set in configuration ([Generic OAuth](https://better-auth.com/docs/plugins/generic-oauth)). Users, sessions and accounts live in D1 `core`. Previews open through Studio, which gives the preview host a short-lived signed token.

**Rejected.** SAML: its libraries are Node-only and unproven on Workers. Better Auth's SSO plugin: it loads those SAML libraries even for OIDC, and some of its features need transactions that D1 doesn't have.

**Consequences.** Full control over the sign-in experience and sessions, but we own the auth code path and its upgrades. The version is pinned at 1.7.6 or later, which includes the fixes for its 2026 security advisories.

## 008 — Agent on the Agents SDK, validated edits only, models chosen per task [#decision-008]

**Context.** The agent must be cheap to run, safe, and unable to damage live sites. The best model for each job will keep changing.

**Decision.** Each conversation is an `AIChatAgent` Durable Object from `@cloudflare/ai-chat` that acts as its owner. Its only write path is the same validated `applyOps` the editor uses, and it has no submit, publish, approve, settings or submissions tools. Models are chosen per task in configuration and called through AI Gateway, with per-brand spend limits. The default for routine edits is GLM-5.3 Flash on Workers AI.

**Rejected.** A fixed number of model tiers with automatic escalation; vector search over uploads; AI judges in the publish path; a second chat stack alongside the Agents SDK.

**Consequences.** Any model can be added or swapped without a code change. The eval suite runs whenever a task's model changes.

## 007 — One live, collaborative Durable Object per site, with edits by block ID [#decision-007]

**Context.** Several people, and their agents, may edit the same draft and page at the same time. Page locks would frustrate them.

**Decision.** A site's drafts live in one `SiteDoc` Durable Object built on PartyServer, Cloudflare's library from the PartyKit team for rooms, broadcast and hibernatable WebSockets ([cloudflare/partykit](https://github.com/cloudflare/partykit)). Every change goes through validated `applyOps`, with ops that address blocks by ID and field, never by position, and is broadcast live, with presence showing who is on which page, block and field. The server orders every batch. When two people change the same field, the later write wins and the other person is told. A rich text field is one value; presence marks who is typing in it.

**Rejected.** Page locks (too restrictive); drafts in D1 (no live ordering point); a CRDT for the whole document (it makes server-side validation hard); RFC 6902 JSON Patch (its array paths are positional, so a concurrent insert makes an op hit the wrong block); Yjs for rich text (a second sync system beside the ops, with its own undo, validation and history).

**Consequences.** Live collaboration with one rule. Two people can't type in the same paragraph with shared cursors; that isn't in this version. The same op vocabulary drives the editor, agent tools, undo and merging ([017](#decision-017)). The editor's behaviour under live remote changes is proven early in the [build plan](/build-plan#4-live-co-editing) (see [025](#decision-025)).

## 006 — Block versions: v1, v2, v3 for editors, any number live [#decision-006]

**Context.** [Decision 001](#decision-001) needs a concrete scheme that stays simple for editors.

**Decision.** Editors see versions as v1, v2, v3. Underneath, each released version has an opaque ID, and each draft's lockfile records those IDs. Released versions are frozen with no exceptions; any change to output is a new version, including urgent fixes, and the platform team can create upgrade drafts on every affected site. Any number of versions can be live at once. Studio encourages upgrades but never forces them. A version is kept while any draft or live release uses it, and for 3 months after the last one stops; the latest version of every block is always kept.

**Rejected.** A cap on live versions; major, minor and patch semantics with auto-applied patches; in-place fixes to released versions; keeping every version for as long as any retained release uses it.

**Consequences.** Upgrades are always a deliberate change through a draft and the site's workflow. Bundle size and visual-test time grow with the number of live versions, so CI tracks both. Rollback can't reach a release whose versions have been removed. Frozen versions still share primitives, Tailwind and React, so a dependency upgrade can change an old version's output; an intended change is accepted through a reviewed, audited screenshot update.

## 005 — Own the page schema; Puck edits it through an adapter [#decision-005]

**Context.** Every site is stored in the page format, so it must be stable and suited to agent edits. Puck's format is still evolving and nests blocks by position.

**Decision.** Our own schema (see [012](#decision-012)), with a flat block map in json-render's style, is canonical. Puck reads and writes it through a tested adapter. From json-render we borrow the catalog-to-prompt and streamed-patch ideas, not its renderer.

**Consequences.** One adapter to maintain. Content never depends on Puck, so the editor could be replaced. [Decision 025](#decision-025) did replace it: our own editor edits this schema directly, with no adapter.

## 004 — Publish immutable snapshots, render on request, cache per release [#decision-004]

**Context.** Live sites must never change by surprise, and publishing and rollback should be fast.

**Options.** (a) Pre-render every page to static HTML at publish. (b) Freeze content, theme and block versions in a snapshot and render on request, caching by release.

**Decision.** (b). A snapshot is a manifest plus one object per page, stored by content hash, so snapshots share unchanged pages and a render reads only the page it needs. Publishing and rollback are pointer changes: the site's Durable Object records the live release, and KV and D1 hold copies of it.

**Consequences.** No build pipeline and no archive of old assets. Shared code outside blocks can still affect live pages, so the visual regression gate covers it.

## 003 — Four Workers: a web and API pair for sites and for Studio [#decision-003]

**Context.** Public sites need to be fast and mostly static. Studio is a rich app. Separating web layers from API layers gives clean boundaries, matching the starter's pattern.

**Decision.** `sites` (Astro) renders public sites and previews, and forwards form posts to `sites-api`, which owns form intake and later payment webhooks. `studio` (TanStack Start with our [editor](/editor)) is the UI, and calls `studio-api` over RPC. `studio-api` owns domain logic, permissions, the Durable Objects and scheduled jobs. All four share packages.

**Rejected.** A single Worker per side (mixes UI and data access); separate Workers for rendering, the agent, forms and jobs (too many moving parts).

**Consequences.** Each UI talks to data only through its API. `sites-api` is small at first and grows when payments arrive.

## 002 — Host on Cloudflare [#decision-002]

**Context.** Pakshi needs global hosting, storage, AI access, custom domains and SSO for many sites.

**Decision.** Cloudflare: Workers, Durable Objects, D1, R2, KV, AI Gateway, the Agents SDK, Cloudflare for SaaS and Email Service.

**Consequences.** One platform covers almost every need. Email Service sending is in beta, which we accept. Snapshots are plain JSON, so content stays portable.

## 001 — Sites pin block versions [#decision-001]

**Context.** All sites render from one central block library. A major change to a block, such as a hero that renders differently on mobile, would reach every site at once. For some sites that change may not fit how they use the block.

**Options.** (a) Every site always uses the latest version of every block. (b) Each site depends on specific block versions and upgrades deliberately.

**Decision.** Option (b). Each site depends on specific block versions. The UI warns when a site is behind, and adopting an upgrade creates a draft that can be previewed.

**Consequences.** Live sites are never changed by surprise. The platform must keep old block versions working, and track and nudge sites that fall behind. The scheme is defined in [006](#decision-006).

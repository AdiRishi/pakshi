## 021 — No spam protection on forms in the MVP [#decision-021]

**Context.** The design gave every site its own Turnstile widget, but non-Enterprise accounts are limited to 20 widgets ([plans](https://developers.cloudflare.com/turnstile/plans/)). Honeypots and rate limits add setup and edge cases for little early value.

**Decision.** Forms ship without spam protection. To keep an unprotected form from sending mail to any address a visitor types, forms send no email to submitters; notifications go only to the form's configured addresses.

**Consequences.** Spam can reach the submissions database until protection is added. When it is, one widget covers the sites domain and its subdomains, and custom domains are grouped 10 to a widget.

## 020 — Share drafts like documents [#decision-020]

**Context.** People need to show drafts to colleagues and to people outside the organization, and to invite others to edit.

**Decision.** Drafts are shared like documents: with named people, the whole organization, or anyone with the link, and the person sharing chooses view or edit access for each. Every draft has a preview link at an address that can't be guessed, served from a fixed R2 key that each save overwrites; KV is too slow to show the latest save. Editing always needs a signed-in Pakshi user, so a link shared for editing gives everyone else view access. Edit access through a share covers one draft and never includes submitting or publishing.

**Rejected.** Previews visible to signed-in staff only; frozen previews with fixed expiry times.

**Consequences.** A preview lives as long as its draft and always shows its latest saved state. Approvers still review a frozen submission snapshot.

## 019 — Brand changes reach sites as drafts; no brand locks [#decision-019]

**Context.** A brand theme change would otherwise ship with whatever unrelated change a site publishes next. Brand locks, which limit what sites may change, add a validator, hidden controls and agent rules.

**Decision.** Sites use their brand's theme and identity as they are, with no overrides and no locks. Each save of a brand's theme, logo or favicon is an immutable brand revision, and each draft pins one, the way its lockfile pins block versions. A new revision creates a Brand update draft on every site in the brand, or moves an unpublished one forward, and it follows that site's workflow. Other drafts keep their pinned revision until they merge after the update is live. The same mechanism creates block upgrade drafts on every affected site.

**Rejected.** Brand locks and site theme overrides in the MVP; theme changes that ride along with the next publish.

**Consequences.** A site that needs a different look belongs to a different brand. Locks can be added later if a real need appears.

## 018 — Media files never change [#decision-018]

**Context.** Replacing a file everywhere it's used would change live sites without a publish.

**Decision.** Each upload is a new file with its own ID, and files are never replaced or versioned. A new image appears only where someone swaps it in. The brand logo and favicon are brand settings that point at a file, so changing them reaches sites through Brand update drafts ([019](#decision-019)). A file is kept while any draft or live release uses it, and for 3 months after the last one stops.

**Consequences.** A media ID always renders the same file. Changing a common asset other than the logo or favicon means updating each place it's used.

## 017 — Named drafts that merge like branches [#decision-017]

**Context.** With one shared draft per site, one person's unfinished page blocks another person's urgent fix or ships with it, and a second submission replaces the first.

**Decision.** A site has one live release and any number of named drafts, each starting from a release. Publishing a draft makes it live, and every other draft is then behind. A draft that's behind must be updated before it can be edited further or submitted. Updating is a three-way merge by block ID and field. Different fields, blocks or pages merge automatically; conflicts (same field on both sides, edit against removal, the same list reordered on both sides) need a person, and a model may suggest a merge for text. A submission under review that merges cleanly keeps its approvals; one that needed a person restarts its workflow.

Four rules keep merges safe. All sides are migrated to the newest block version any of them uses before diffing. The merged draft is validated like a submission, and a failure is a conflict. A submission publishes only if it's based on the current live release. And publishing closes a draft only if nobody edited it after it was submitted.

**Rejected.** One draft per site; publishing chosen pages from a shared draft; a draft per page.

**Consequences.** More to build: a drafts list, the merge engine and a conflict screen. The merge engine is a Phase 0 spike. Several people can still edit one draft live together ([007](#decision-007)).

## 016 — Keep all site data [#decision-016]

**Context.** Form submissions and past releases are part of a site's data.

**Decision.** Nothing deletes submissions or releases automatically. They are kept for as long as the site exists. A single submission, or everything for one person, can be deleted on request.

**Consequences.** Storage grows over time, which D1 and R2 handle comfortably. Rollback can target any earlier release whose block versions and media are still retained ([006](#decision-006), [018](#decision-018)).

## 015 — Approval workflows on the organization, a brand or a site [#decision-015]

**Context.** Review requirements differ between sites and brands, and the people who own a site know them best.

**Decision.** Workflows can be set on the organization, a brand or a site, and the nearest one applies. A workflow is an ordered list of any number of steps, including none, each naming who can approve (roles or people) and how many approvals it needs. Definitions and each submission's progress are rows in D1; completing the last step publishes. The MVP editor is a list of steps. A visual, node-based editor built with an off-the-shelf flow library can follow, on the same definitions.

**Rejected.** A fixed cap on approval steps; a general-purpose workflow engine.

**Consequences.** Owners at each level control their own review process without platform changes. Editing a workflow is a permission, so whoever holds it controls how a site publishes.

## 014 — Fine-grained permissions, with roles as bundles and per-person overrides [#decision-014]

**Context.** Brands are just groupings of sites; what people may do must be controlled precisely and the same way everywhere.

**Decision.** Permissions are fine-grained named actions, and they decide what a person can do. Roles are sets of permissions for giving access quickly, with defaults shipped by Pakshi and custom roles created by admins. Grants give a person a role on the organization, a brand or a site, and inherit downward. An override switches one permission on or off for one person on one scope and beats any role. A person can grant only permissions they hold, on scopes they control. One `authorize` function in `packages/domain` is used by the API, the agent's tools, live editing and Studio's UI.

**Consequences.** One place to reason about access. New features add permissions rather than new checks. Rules such as self-approval are permissions, so admins decide them.

## 013 — Integrate Puck through a sync module and a patch; don't fork [#decision-013]

**Context.** Live collaboration needs Puck to accept changes from others without losing the user's place or undo. Puck has no collaboration support. Its core is about 24,000 lines of TypeScript under the MIT license, built on a zustand store with a reducer of small actions ([source](https://github.com/puckeditor/puck)).

**Options.** (a) Fork Puck. (b) A sync module on Puck's public API, plus patches where the API falls short. (c) Build our own editor.

**Decision.** (b). Puck already exposes what the sync needs: an `onAction` callback for every local change, small actions (insert, move, remove, replace) we can dispatch for remote changes, a flag to keep them out of its history, and lookup by block ID. Puck's actions address blocks by index, so the sync module converts our ID-based ops using that lookup. The biggest gap is undo, which restores whole-page snapshots, erasing other people's changes, and has hard-wired shortcuts; a pnpm patch replaces its history slice and shortcuts, and we offer the change upstream. Smaller gaps, such as fresh IDs on replayed inserts, index-based selection and focused fields that ignore remote changes, are handled in the sync module and covered by the Phase 0 spike.

**Rejected.** A fork: we would own drag and drop, the canvas iframe and every field type, and fall behind an actively developed 0.x library. Our own editor: much larger, for no gain in the MVP.

**Consequences.** We keep Puck's upgrades, and re-check the patch on each one. If the Phase 0 spike shows the public API can't support live editing well, we revisit a fork with evidence.

## 012 — Effect Schema instead of Zod [#decision-012]

**Context.** The starter defines shared schemas with Effect Schema (Effect v4). The earlier design assumed Zod 4.

**Decision.** Use Effect Schema as the one schema library for pages, blocks, edit operations and agent tools. It produces Standard Schema and JSON Schema, which cover Puck field generation and agent tool definitions.

**Consequences.** One schema library and one style across the repo. Libraries that expect Zod specifically (for example some json-render helpers) are used only through JSON Schema, or not at all.

## 011 — Build on application-platform-starter [#decision-011]

**Context.** A starter already exists with a monorepo pattern and utilities for Cloudflare apps ([repo](https://github.com/AdiRishi/application-platform-starter)).

**Decision.** Pakshi starts from it: pnpm and Turborepo, Alchemy for all infrastructure and bindings (instead of Wrangler configs), Effect for application services, oxlint and oxfmt with its lint rules, TypeScript 7, Vitest, Playwright, and Blume docs with repository ADRs. Its `apps/web` becomes `apps/studio`, and `apps/sites` is added for Astro.

**Consequences.** A working foundation from day one. Alchemy is a beta dependency pinned (with a patch) by the starter, so upgrades are deliberate. PartyServer and `AIChatAgent` Durable Objects are plain classes, outside the starter's Effect-based Durable Object pattern, which Phase 0 checks.

## 010 — Workers Paid plan; no Enterprise features, no root domains [#decision-010]

**Context.** Pakshi should not need a Cloudflare Enterprise subscription.

**Decision.** Run production on the Workers Paid plan (from $5 a month per account plus usage). The Free plan's 10 ms CPU per request, 100,000 requests a day and missing Email Service sending rule it out for production. The only Enterprise-only feature in the earlier design, apex proxying for root domains, is dropped: sites use subdomains such as www, and owners redirect the root domain at their DNS provider.

**Consequences.** Predictable, low cost. Any future feature that needs Enterprise must be raised as a new decision.

## 009 — Staff sign-in with Better Auth over OIDC, not Cloudflare Access [#decision-009]

**Context.** Staff need SSO with the organization's identity provider. Cloudflare Access works at the network edge, which limits how much control Studio has over the sign-in experience and sessions.

**Decision.** Run our own auth with Better Auth in `studio-api`. Its SSO plugin connects to the organization's identity provider over OIDC ([SSO plugin](https://better-auth.com/docs/plugins/sso)). Users, sessions and accounts live in D1 `core`. Previews open through Studio, which gives the preview host a short-lived signed token.

**Rejected.** SAML: its libraries are Node-only and unproven on Workers.

**Consequences.** Full control over the sign-in experience and sessions, but we own the auth code path and its upgrades. The version is pinned at or above the latest security release. The plugin's `resolveUser` and `guardProviderMutation` need transactions that D1 doesn't have, so they stay off.

## 008 — Agent on the Agents SDK, validated edits only, models chosen per task [#decision-008]

**Context.** The agent must be cheap to run, safe, and unable to damage live sites. The best model for each job will keep changing.

**Decision.** Each conversation is an `AIChatAgent` Durable Object from `@cloudflare/ai-chat` that acts as its owner. Its only write path is the same validated `applyOps` the editor uses, and it has no submit, publish, approve, settings or submissions tools. Models are chosen per task in configuration and called through AI Gateway, with per-brand spend limits. The default for routine edits is GLM-5.3 Flash on Workers AI.

**Rejected.** A fixed number of model tiers with automatic escalation; vector search over uploads; AI judges in the publish path; a second chat stack alongside the Agents SDK.

**Consequences.** Any model can be added or swapped without a code change. The eval suite runs whenever a task's model changes.

## 007 — One live, collaborative Durable Object per site, with edits by block ID [#decision-007]

**Context.** Several people, and their agents, may edit the same draft and page at the same time. Page locks would frustrate them.

**Decision.** A site's drafts live in one `SiteDoc` Durable Object built on PartyServer, Cloudflare's library from the PartyKit team for rooms, broadcast and hibernatable WebSockets ([cloudflare/partykit](https://github.com/cloudflare/partykit)). Every change goes through validated `applyOps`, with ops that address blocks by ID and field, never by position, and is broadcast live, with presence showing who is on which page, block and field. The server orders every batch. When two people change the same field, the later write wins and the other person is told. A rich text field is one value; presence marks who is typing in it.

**Rejected.** Page locks (too restrictive); drafts in D1 (no live ordering point); a CRDT for the whole document (it makes server-side validation hard); RFC 6902 JSON Patch (its array paths are positional, so a concurrent insert makes an op hit the wrong block); Yjs for rich text in the MVP (a second sync system beside the ops, with its own undo, validation and history, and Puck's rich text field would fight it).

**Consequences.** Live collaboration with one rule. Two people can't type in the same paragraph with shared cursors; that is on the Later list. The same op vocabulary drives Puck sync, agent tools, undo and merging ([017](#decision-017)). Puck's behaviour under live remote changes is the first Phase 0 spike (see [013](#decision-013)).

## 006 — Block versions: v1, v2, v3 for editors, any number live [#decision-006]

**Context.** [Decision 001](#decision-001) needs a concrete scheme that stays simple for editors.

**Decision.** Editors see versions as v1, v2, v3. Underneath, each released version has an opaque ID, and each draft's lockfile records those IDs. Released versions are frozen with no exceptions; any change to output is a new version, including urgent fixes, and the platform team can create upgrade drafts on every affected site. Any number of versions can be live at once. Studio encourages upgrades but never forces them. A version is kept while any draft or live release uses it, and for 3 months after the last one stops; the latest version of every block is always kept.

**Rejected.** A cap on live versions; major, minor and patch semantics with auto-applied patches; in-place fixes to released versions; keeping every version for as long as any retained release uses it.

**Consequences.** Upgrades are always a deliberate change through a draft and the site's workflow. Bundle size and visual-test time grow with the number of live versions, so CI tracks both. Rollback can't reach a release whose versions have been removed. Frozen versions still share primitives, Tailwind and React, so a dependency upgrade can change an old version's output; an intended change is accepted through a reviewed, audited screenshot update.

## 005 — Own the page schema; Puck edits it through an adapter [#decision-005]

**Context.** Every site is stored in the page format, so it must be stable and suited to agent edits. Puck's format is still evolving and nests blocks by position.

**Decision.** Our own schema (see [012](#decision-012)), with a flat block map in json-render's style, is canonical. Puck reads and writes it through a tested adapter. From json-render we borrow the catalog-to-prompt and streamed-patch ideas, not its renderer.

**Consequences.** One adapter to maintain. Content never depends on Puck, so the editor could be replaced.

## 004 — Publish immutable snapshots, render on request, cache per release [#decision-004]

**Context.** Live sites must never change by surprise, and publishing and rollback should be fast.

**Options.** (a) Pre-render every page to static HTML at publish. (b) Freeze content, theme and block versions in a snapshot and render on request, caching by release.

**Decision.** (b). A snapshot is a manifest plus one object per page, stored by content hash, so snapshots share unchanged pages and a render reads only the page it needs. Publishing and rollback are pointer changes: the site's Durable Object records the live release, and KV and D1 hold copies of it.

**Consequences.** No build pipeline and no archive of old assets. Shared code outside blocks can still affect live pages, so the visual regression gate covers it.

## 003 — Four Workers: a web and API pair for sites and for Studio [#decision-003]

**Context.** Public sites need to be fast and mostly static. Studio is a rich app. Separating web layers from API layers gives clean boundaries, matching the starter's pattern.

**Decision.** `sites` (Astro) renders public sites and previews, and forwards form posts to `sites-api`, which owns form intake and later payment webhooks. `studio` (TanStack Start with Puck) is the UI, and calls `studio-api` over RPC. `studio-api` owns domain logic, permissions, the Durable Objects and scheduled jobs. All four share packages.

**Rejected.** A single Worker per side (mixes UI and data access); separate Workers for rendering, the agent, forms and jobs (too many moving parts).

**Consequences.** Each UI talks to data only through its API. `sites-api` is small at first and grows when payments arrive.

## 002 — Host on Cloudflare [#decision-002]

**Context.** Pakshi needs global hosting, storage, AI access, custom domains and SSO for many sites.

**Decision.** Cloudflare: Workers, Durable Objects, D1, R2, KV, AI Gateway, the Agents SDK, Cloudflare for SaaS and Email Service.

**Consequences.** One platform covers almost every need. Email Service sending is in beta, which we accept. Snapshots are plain JSON, so content stays portable.

## 001 — Sites pin block versions [#decision-001]

**Context.** All sites render from one central block library. A major change to a block, such as a hero that renders differently on mobile, would reach every site at once. For some sites that change may not fit how they use the block.

**Options.** (a) Every site always uses the latest version of every block. (b) Each site depends on specific block versions and upgrades deliberately.

**Decision.** Option (b). Each site depends on specific block versions. The UI warns when a site is behind, and adopting an upgrade creates a draft that can be previewed.

**Consequences.** Live sites are never changed by surprise. The platform must keep old block versions working, and track and nudge sites that fall behind. The scheme is defined in [006](#decision-006).

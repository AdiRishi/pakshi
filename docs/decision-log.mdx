## 095 — Blocks are built on a shared kit, and designed in a lab [#decision-095]

**Context.** Each block version wrote its own section wrapper, heading, buttons and spacing, so blocks drifted apart and none used shadcn/ui's component recipes. Checking a block's look meant running the whole stack and opening Studio.

**Decision.** `packages/blocks/src/kit/` holds what most blocks share: `Section` (surface, spacing, backdrop and an inset panel), `Intro` and `Heading` (a short label, a heading with a softer continuation, an introduction), `Actions` and `buttonClass` (shadcn/ui's button variants in the theme's tokens), `Icon`, `Disclosure`, `Marquee` and `Scroller`. Blocks use the theme utilities only, as before. `pnpm --filter @repo/blocks lab` serves a page that renders every fixture of the newest versions, or a whole page in any theme, with Vite and the same site stylesheet.

**Consequences.** Like the field components, the kit is shared by frozen versions, so a change to it that alters their output needs a rendering changes entry. The lab needs no Cloudflare profile, so block design and review no longer wait on a stack.

## 094 — A block version can rename the layouts of the one before it [#decision-094]

**Context.** `migrate` turned the previous version's props into the next one's, but layouts kept their names forever, so a version could only add layouts. Redesigning a block meant keeping names such as `three-columns` that no longer described a layout, once columns became a choice.

**Decision.** A version lists `renamedVariants`, the previous version's layouts it calls by another name, and upgrading moves content onto them. `migrate` is told the layout the content had, so it can carry what the old layout meant into props, such as `two-columns` into a `columns` choice. A presentation labels renamed layouts in `retiredVariants`, because sites on older versions still show them. A test checks every old layout lands on one the new version has.

**Consequences.** Old migrations take one argument and still type-check. The editor's layout picker and the agent see only the pinned version's layouts.

## 093 — Blocks offer choices and icons as fields [#decision-093]

**Context.** A block's look was one variant, so every combination of columns, alignment, image side and card style needed a variant of its own. Feature lists had no icons.

**Decision.** Two field kinds join the others. A `choice` is a block-level setting with a few named options. Its first option is what new content starts with and what content without the key reads as, so headers and footers created empty, and content migrated from older versions, are complete without it. The editor shows choices under Layout and style, labelled by the block's presentation, which can name the layouts a choice applies to. An `icon` names an icon from a curated set of Lucide symbols and social networks' marks, picked from a searchable grid. Merging treats both as single values.

**Consequences.** Variants are kept for genuinely different arrangements. An icon name stays in the set for as long as any page might use it, since released versions' golden schemas list the names.

## 092 — Themes set color mode, a second color, type styles, buttons, cards and width [#decision-092]

**Context.** Studying about fifty well-known sites, most of the difference between them came from a few choices the theme couldn't make: whether the site is dark, a second brand color, how headings are tracked and cased, how small labels look, pill or squared buttons, whether cards are outlined, filled or raised, and how wide the page runs. Display type also topped out near 50px where the sites use 64 to 140px.

**Decision.** `ThemeValues` gains `colorMode` (light, dark or the visitor's), `accentColor` (optional), `headingStyle`, `labelStyle`, `buttons`, `cards` and `width`; the type scale gains two sizes and fluid steps, heading weight gains light and regular, the font list grows to 28, and two surfaces join the four: `tint`, a pale wash of the brand, and `accent`, the second color or a light shade of the first. Card style replaces shadow. The resolved theme becomes `pakshi.theme/2`. A revision, draft or snapshot stored in the first schema reads as the second: its colors stay as they were, its new surfaces are generated from its brand surface's color, and its shadow becomes its card style.

**Rejected.** Presets, for the reasons in [087](#decision-087). Migrating stored themes, which would mean rewriting immutable snapshots.

**Consequences.** Old snapshots render as before, except that type and spacing utilities now follow the new scales, which released block versions share; their changed screenshots are recorded in the rendering changes log. A theme that is always light or dark shows in that scheme in the editor whatever the scheme switch says.

## 091 — Blogs are pages that hold posts [#decision-091]

**Context.** A blog post was a page with `type: "post"` at any address. A blog list showed every post on the site, and the site had one feed at `/blog/rss.xml`. That gives a site one blog in practice. An organization with news and stories couldn't keep them apart, a home page couldn't show the latest news without the stories, and moving the news section meant changing every post's address.

**Decision.** A collection is a page that holds entries of one built-in kind, and an entry is a page in a collection. Both are page documents, so ops, history, previews, approvals and merging work on them unchanged. The one kind is a blog, whose entries are posts. People see "Blog" and "posts", as in Squarespace, and a blog can be named anything, such as News. The code uses the same words for the kind (`blog`, `PostMeta`, the `blog` and `post` recipes, `post-header`) and keeps `collection` and `entry` for the structure.

- An entry stores only a slug. Its address is its collection's address plus the slug, resolved in one place, `listingsOf`. Moving a blog moves its posts with no ops on them, and a merge where one side moves the blog while the other adds a post puts the post at the new address. A post never moves to another blog, and a collection's kind never changes.
- The document module keeps the rules: a post goes only in a blog, a blog with posts can't be deleted, an entry's address changes only through the new `setSlug` op, and no two addresses collide after a batch. A post is served only when it and its blog are both published.
- A merge decides a blog that one side removed together with its posts. If the keeping side left the blog and its posts as they were, the blog goes; otherwise one conflict keeps or removes them all.
- `post-list@2` shows one blog, named by a `collection` field, with a `number` field for how many posts. On its own blog's page it pages through every post with `?page=N`. Elsewhere it shows the newest and links to the blog. `post-header@1` shows a post's details from its meta, and its `entryOf: "blog"` keeps it to posts.
- `post-list@1`, which listed every post on the site, is deleted with its fixtures, golden file and screenshots instead of being kept beside version 2. "Every post" means nothing once a site has several blogs, and stages start empty, so no site uses it.

**Rejected.** A full address stored on each post, which would need an op per post to move a blog and would put a post added during a move at the old address. One listing block for every kind, when each kind lists its entries in its own way. A blog page that lists its posts by itself, which would take the layout away from editors; the list is a block they place and can move. Kinds defined by editors, with schemas and migrations, when built-in kinds cover what sites build.

**Consequences.** RSS moves from `/blog/rss.xml` to one feed per blog at the blog's address plus `/rss.xml`, and a redirect from a blog's old address covers its posts and its feed. A second kind adds a `CollectionKind` literal, an entry member in the page and listing unions, an entry in `collectionKinds`, two recipes, a listing and a header block, with no change to addresses, merging, freezing or ops. A batch holds at most 500 ops, so deleting a blog with more posts than that takes several batches, each undone on its own. Documents saved before this change don't decode, so local stacks that hold them are destroyed and started again.

## 090 — Studio sets its color scheme with a head script, and site previews keep their own [#decision-090]

**Context.** People working in Studio at night asked for a dark mode. Studio should follow the device's setting, let someone choose light or dark instead, and never show the wrong scheme while a page loads. Studio renders on the server, but only the browser knows the device's setting.

**Decision.** Studio uses shadcn's theming: a `.dark` class on the html element switches the theme variables in `globals.css`, and Tailwind's `dark` variant follows it. The choice of System, Light or Dark is kept in `localStorage`. A small script in the document's head reads it, or the device's setting for System, and sets the class before the page paints. A `useTheme` hook follows the setting, the stored choice and other tabs as they change. The dark palette is the brand's own: navy surfaces that get lighter the higher they sit, the sky blue kept for primary actions and focus, and a lighter sky blue for links. The editor's outlines, warnings and presence colors draw on the site's page, so they stay the same in both schemes.

**Rejected.** A cookie the server reads, which can't know the device's setting, so System would flash on first load; `next-themes`, which does little more than the script and the hook do.

**Consequences.** The html element's class is set outside React, so the root route tells React to ignore it while hydrating. A color added to `globals.css` needs a dark value too, unless it draws on a site's page.

## 089 — The checks open from the top bar, and Pakshi fixes what it can of them [#decision-089]

**Context.** In user testing, clicking the top bar's count of things to fix seemed to do nothing, and people expected the agent to fix the issues for them. The agent couldn't edit menus, redirects or forms, and it read the issues without the IDs it edits by.

**Decision.** The count opens a popover with the same list the submit dialog shows: every check, passed or with its issues. Choosing an issue goes to it: its block or field, on its page if that's another one, a page's own settings, Pages and menus, or the site's forms settings. A block to select is part of the editor's address only until the page has opened. "Fix all with Pakshi" shows the chat and sends Pakshi a message listing the issues, as if the person had typed it. It's disabled, with the reason, while Pakshi is working on another request, can't be reached, or the draft no longer takes the person's changes. The agent edits menus, redirects and forms, publishes an unpublished page again after asking, and reads the issues with `check_draft`. Three kinds of issue only a person fixes: choosing an image, writing or accepting alt text, and setting where a form's entries go. One rule in `@repo/agent/issues` names them, so the popover marks them "Needs you" and leaves them out of the message, and the agent leaves them alone.

**Rejected.** Letting the agent write alt text with the vision model, which would skip the person confirming it; letting it choose images from the library, which it can't see.

**Consequences.** The panel that stepped through issues one at a time is gone. A new check needs an issue kind, its description, where it's fixed, and whether only a person can fix it.

## 088 — Blocks are named and shown from files beside their released versions [#decision-088]

**Context.** Studio's Blocks area is being redesigned for people who have never built a site: a gallery of every block, shown live in the order a page runs, and a page per block to try its layouts. A block's title lived in its released folder, which never changes, so it couldn't be made plain, and the editor named layouts by turning variant IDs such as `split-image` into words. Placeholder fixtures can't change either, and some fail as showcases: boats as team photos, landscapes as logos, no map in a location.

**Decision.** Each block type keeps `presentation.ts` and `sample.ts` in `src/<type>/`, outside its version folders, and the registry generator lists both. A presentation gives the block's name, following the names site builders use, such as Hero, Features and Testimonial; a one-line summary; a hint; a label and description for each layout; how a list names its items; field labels and hints; the optional fields a layout needs; and the block's place in the gallery. `defineBlock` keeps the types of a version's fields and variants, so the compiler checks a presentation against the newest version, and a test catches one left on an older version. A contract's title and field titles come from it, so Studio, the editor and the agent use the same words. A sample is showcase content for the newest version, with images drawn for samples, and `blockShowcase` builds a throwaway draft of the fixture site around one. Studio shows blocks live, scaled from desktop width, rendering each preview only as it comes near the viewport.

**Rejected.** New block versions only to change names or sample content, which would ask every site to adopt an upgrade that changes nothing they show.

**Consequences.** Renaming a block or a layout is an ordinary change. A new block version must update its type's presentation and sample, which the tests enforce. Golden contracts no longer pin titles.

## 087 — Brands store every theme value, with no presets [#decision-087]

**Context.** A brand's theme was one of three presets, Civic, Editorial or Bold, with the values its admins changed on top, which it kept if it picked another preset. Nobody picks a preset and leaves it: brands change the values, so the preset decides little and adds a choice to explain.

**Decision.** A brand's theme is every value the styling system has: brand color, neutral tone, fonts, type scale, heading weight, corner radius, shadow, density, image corners and motion. Each revision stores them whole, and Theme Studio edits each one directly. A new brand starts from the default theme in `@repo/tokens`, which has the Editorial preset's values, in the brand color its admin picks. No stored data was migrated: every stage starts empty, and stages made before this change are destroyed and made again.

**Rejected.** Storing only the values a brand changed from the default, which would restyle every brand whenever the default changes.

**Consequences.** A code change to the default theme reaches only brands made after it. What keeps sites from looking generic is the strong default and the bounded token choices ([vision](/vision#brands-and-theming)).

## 086 — Block requests are kept in Pakshi, not filed in an outside tracker [#decision-086]

**Context.** The plan had block requests filed into the platform team's tracker. The team may later want people to annotate pages to explain what they need, or to hand requests to an agent or to GitHub.

**Decision.** Requests live in D1. People file them from the block catalog, for one site they may ask for blocks on or for any site, and the agent files its person's the same way, both held to `blocks.request`. The platform team, who may upgrade blocks across the organization, reads every request in the catalog and closes each once answered; everyone else sees their own.

**Consequences.** No outside service, token or stand-in. Sending requests elsewhere later reads them from D1.

## 085 — Alerts and the security review move out of checkpoint 11 [#decision-085]

**Context.** Checkpoint 11 listed alerts for the failures operations names, and a security review as a check. Workers Issues and Cloudflare's alerting only work in production, and several failures, such as unsent emails, never throw.

**Decision.** Workers Logs and tracing stay on for every Worker, and AI Gateway reports model cost and errors. Alerts on top of them are set up later, outside the build plan's checkpoints. Security gets scans of its own, apart from building features. A first review of this checkpoint found one gap to close then: an override lets someone who manages a brand or site's members switch permissions off for a person who holds more than they do, an org admin included.

**Consequences.** The operations section names observability and success metrics only.

## 084 — Sites use Astro's content security policy, sent by built sites only [#decision-084]

**Context.** Every site must send a strict content security policy. Pages run no scripts, load the site's own styles, fonts and images, and inline one stylesheet: the theme, which differs per site.

**Decision.** Astro's `security.csp` sends each page's policy as a header, with the directives in `astro.config.ts`, hashes of what Astro inlines, and the theme's hash added at render with `Astro.csp.insertStyleHash`. The middleware gives every other response a policy that loads nothing, and every response `nosniff` and a referrer policy. Astro's dev server injects scripts of its own, so Astro sends no page policy there.

**Rejected.** A policy of our own in the middleware, which would block the dev server's scripts, or need loosening for it.

**Consequences.** The page policy can only be seen in a deployed site, which checkpoint 12 checks.

## 083 — Success metrics are worked out from what Pakshi records anyway [#decision-083]

**Context.** Every success metric must be recorded, and the Pakshi team needs somewhere to read them.

**Decision.** studio-api works each one out on request, over a period, from D1's copies of releases and submissions, the audit log and block requests: time to launch and approval turnaround in business days, time to change in minutes, agent success from the agent's turns and their undos, untracked changes from the times the reconcile job put a site's live release back, and block requests per active site by month. Org admins read them on a Metrics page. The agent's cost per launch stays in AI Gateway, which tags every model call with its site.

**Rejected.** Counting tokens and pricing model calls in Pakshi, which copies what AI Gateway already keeps.

**Consequences.** A new metric is a query, not new recording, wherever its events are audited.

## 082 — The audit log is written by whatever makes each change [#decision-082]

**Context.** Every audited action must be recorded, and actions happen in studio-api, in each site's `SiteDoc`, and in scheduled jobs.

**Decision.** One `audit_log` table in D1. studio-api writes the entries for what it changes. `SiteDoc` sends its own through its outbox, written in the same storage turn as the change; the entries for publishes and rollbacks are made from the release records as they reach D1, so no release goes live without one. An editing session is one entry, for a person's run of edits in a draft until half an hour passes without one, rewritten with each batch as it grows. An entry deleting a person's form entries doesn't keep their email address. Entries outlive the sites they name. Reading the log needs `audit.read`, which org admins hold.

**Consequences.** Every new audited action is one event in `AuditEvent`, with its kind in the log's filters.

## 081 — Custom roles are rows in D1, held to the delegation rule [#decision-081]

**Context.** Admins create custom roles, and people change who holds what, but no one may give more than they hold.

**Decision.** Default roles stay in code and can't be changed; custom roles are rows in D1, and a grant names either by ID. Making or changing a role needs `roles.manage` and every permission it held and holds, across the organization. Giving, changing or taking away a role on a scope, and setting or removing an override, needs `members.manage` there and every permission involved. A role someone holds, or a workflow step names, can't be deleted, and the last org admin can't lose the role, which a trigger in D1 holds to when two admins give it up at once. Workflow steps name roles by ID and show their current names.

**Consequences.** Editing a custom role changes what everyone who holds it may do at once.

## 080 — SiteDoc keeps each person's permissions, for live and agent batches alike [#decision-080]

**Context.** [Decision 041](#decision-041) kept a person's permissions on each live connection's socket. The agent's batches carried a flag captured when its conversation opened, so it would keep editing after its person lost `page.edit`.

**Decision.** `SiteDoc` keeps what each person may do on the site in its own storage. studio-api records it when someone opens a live connection or a conversation with the agent, and a grant, override or role change sends every site it covers what the people it changed may do now, before the change returns. If a site can't be told, the change fails as one to try again, and trying again tells every site again even though D1 already holds it. Live and agent batches are both checked against it, and `SiteDoc` closes the connections of anyone who can no longer edit their draft.

**Consequences.** A removed permission stops the next batch from a person and their agent alike.

## 079 — Pre-flight becomes the checks, with no heading rules, and a panel to fix them [#decision-079]

**Context.** "Pre-flight" read as jargon. The spec asked it to check heading order, alt text, link text and form labels; blocks fix their own heading levels, so the only heading problem an editor could cause is a page without an h1, which is fine for many pages.

**Decision.** The checks, as Studio and the docs now call them, add two rules: links that show no text, in rich text and menus, and form fields without a label. There is no heading rule. The editor's top bar counts what's left to fix and opens a checks panel beside the canvas, where the chat and outline are, so the settings panel stays in view for fixes made there. It steps through each issue, opening its page and selecting its block or field, and ticks it off once fixed. The issue it's on is part of the editor's address.

**Rejected.** The panel over the settings panel, as the design shows it, which would hide page titles, alt text and form labels while fixing them.

**Consequences.** A new check is an issue kind, its description, and where it's fixed.

## 078 — Site settings leave out a default description and the email sender, for now [#decision-078]

**Context.** The Studio designs show a default description among the General settings and a choice of sender on Forms and email.

**Decision.** Neither is built. Every page needs its own description before it publishes, so a default would never be shown. Choosing a sender needs a sender domain on Cloudflare DNS, which comes with [checkpoint 12](/build-plan#12-production); until then every email comes from the stage's shared sender.

**Consequences.** Adding either later is a field in the settings registry ([decision 072](#decision-072)).

## 077 — Deleted sites are kept for 30 days, then purged by the daily job [#decision-077]

**Context.** A deleted site must stop serving at once, stay restorable by an org admin for 30 days, and then be deleted for good.

**Decision.** Deleting marks the site in D1, takes its hosts out of KV and releases its domains; every list leaves deleted sites out. Restoring clears the mark and puts its platform subdomain back in KV, while its domains have to be added again. The daily job erases each site deleted more than 30 days ago: its `SiteDoc` and `SiteSubmissions` storage, its snapshots and agent documents in R2, its library, and its rows in D1. A brand can be deleted only once it has no sites, counting ones still restorable.

**Rejected.** An alarm on each site's `SiteDoc` to purge itself, which can't reach D1's rows or the site's other objects as simply as one job can.

**Consequences.** The agent's conversations live in their own `SiteAgent`s, named by site, draft and person, which nothing lists; they aren't erased yet, and checkpoint 11's audit work should record them so the purge can.

## 076 — In the dev stack, only `.localhost` domains are proven [#decision-076]

**Context.** Custom domains are proven and served through Cloudflare for SaaS, which needs production. The dev stack still needs to show a site at its own domain.

**Decision.** A domain is a row in D1 with an ownership token, shown as a TXT record beside the CNAME. Checking a waiting domain, on schedule or from Check now, proves a name under `.localhost` at once, since it can only reach the machine Pakshi runs on, and writes its host to KV. Other names wait. Checkpoint 12 replaces the check with Cloudflare for SaaS's verification and certificate status.

**Consequences.** The dev stack serves a site at a domain such as `rooms.riverton.localhost` on the Sites Worker's port.

## 075 — Library images are resized on `sites` with the Images binding [#decision-075]

**Context.** Images must be resized and optimized automatically, and the library keeps one original per file.

**Decision.** Uploads go to R2 as they are, with their format and size read from their own bytes. Blocks give each library image a `srcset` of the widths `sites` serves below its own, and `sites` resizes the original with the Images binding into AVIF or WebP when the browser takes them, caching each copy. When resizing fails, the original is served.

**Rejected.** Cloudflare Images' hosted storage, which would keep a second copy of every file outside R2.

**Consequences.** Studio's editor and previews show originals. Under `alchemy dev` the binding resizes locally.

## 074 — Form notifications retry from `SiteSubmissions`' alarm [#decision-074]

**Context.** Each new entry emails its form's addresses, and a failed send has to be tried again.

**Decision.** `SiteSubmissions` stores each email it owes beside the entry, and its alarm sends what's due, waiting twice as long after each failure, up to six hours. The addresses and the Studio address the emails link to reach it with the site's live settings.

**Rejected.** A scheduled job across all sites, which would have to find every site's waiting emails.

**Consequences.** A site's emails wait only on its own object, and the entry is stored whether or not its email goes.

## 073 — Forms, menus and redirects are edited as whole values in drafts [#decision-073]

**Context.** Forms and menus reached a draft only through merges, carried by the `rebase` op, so people had no way to edit them. Checkpoint 10 adds the form editor, the menus screen, unpublishing pages and redirects.

**Decision.** People's ops set each of these whole: `setForm` and `removeForm` for one form, `setMenu` for one menu, `setRedirect` for one address, and `setStatus` publishes or unpublishes a page. A form can't be removed while a block uses it. Redirects are draft content beside forms, shipped in the snapshot. `rebase` now sets only the base, lockfile and brand revision, and SiteDoc moves a draft's forms, menus and redirects with the same ops people use.

**Rejected.** Ops per form field or menu item, which merge more finely but add a dozen ops for values people rarely edit at the same time; merges still combine menus item by item.

**Consequences.** Two people editing one form at once see the later save win, and the earlier writer is told. Unpublishing a page and taking it out of the menus are one batch from Studio, so one undo reverses both.

## 072 — Site settings are a registry of definitions with one home in SiteDoc [#decision-072]

**Context.** A site's only setting was its name, stored in every draft, changed only by merges, and merged as a conflict. Checkpoint 10 adds a default sharing image, where each form's entries are emailed, and the sender, and more settings will follow. The Studio designs say general settings "aren't part of any draft" and reach the live site with the next publish, while form email settings "take effect as soon as you save."

**Decision.** Each setting is one field in a registry in `@repo/contracts`, with its schema, its default and its delivery. A `published` setting changes what visitors see, so freezing copies it into the snapshot and it goes live with the next publish. A `live` setting changes how the site runs, so it takes effect when it's saved. Every type, the save payload and the snapshot's settings are derived from the registry. `SiteDoc` is the one home: a row per setting someone has set, with who and when; anything unset reads as its default. Saving names the settings revision the screen started from and is refused if someone saved since. A save that changes `live` settings sends them, through the outbox, to the runtime that reads them, which today is the site's `SiteSubmissions`. Drafts, merges and `rebase` no longer carry settings.

**Rejected.** Settings in drafts, which puts every change through approval and can't take effect at once; a home per setting, such as form addresses in `SiteSubmissions`, which needs a new decision for every new setting; settings inherited from brands or the organization, until one needs it.

**Consequences.** A new setting is a field and a default, with no migration. A rollback brings back the published settings its snapshot holds. Settings screens are built by hand and save through one call.

## 071 — Build and test in the dev stack as real people; production comes last [#decision-071]

**Context.** Several checkpoints moved their checks to whichever checkpoint first needed production, which pulled production setup into the middle of the plan. Meanwhile every stage but production seeded test users, a sample site and the block fixture sites, and signed people in through a test identity provider, so tests and demos never went through setting Pakshi up.

**Decision.** Every checkpoint is built and checked in the dev stack, and a final checkpoint deploys production and runs the checks that need Cloudflare's network. Pakshi gains email and password sign-in through Better Auth. An empty stack is set up by its first visitor, who names the organization and becomes its org admin; everyone after joins by invitation with a default role. Org admins create brands, and org and brand admins create sites. The test identity provider, the seeded users and the sample site go. Integration journeys set Pakshi up through Studio, while unit and E2E tests set up whatever data they need ([kinds of tests](/adr/three-kinds-of-tests)). Sign-in through the organization's identity provider returns with production.

**Rejected.** Keeping seeded test users and sites in dev, which tests a Pakshi no one will run; open sign-up, which lets anyone who reaches Studio in.

**Consequences.** `pnpm dev` starts empty. The integration journeys share one setup, made through Studio. Decisions 052 and 070 point at the production checkpoint, and a stage holds one organization, as each deployment of Pakshi does.

## 070 — Measuring `sites` startup moves to checkpoint 9, with production [#decision-070]

**Context.** Checkpoint 8 asks for `sites` startup measured well under 1 second with two versions of one block live. Several versions of the header and hero are live at once in the dev stack, but Cloudflare reports a Worker's startup time only when its code is uploaded, which the local stack never does.

**Decision.** The measurement moves to checkpoint 9, which builds domains and needs production anyway ([decision 052](#decision-052)). Checkpoint 8 is done with versions live at once in the dev stack.

**Consequences.** Until then, nothing checks that dynamic imports keep startup small as the library grows.

## 069 — A brand color too light to read fails the contrast check rather than being changed [#decision-069]

**Context.** Theme Studio generates the palette from one brand color, picks every text color to read clearly on its background, and can't save a theme with a pair that fails WCAG 2.2 AA. Generated pairs always pass, so the only color that can fail is the brand color itself, used for buttons, links and focus outlines on light pages. Pakshi could quietly darken it until it passed.

**Decision.** The light scheme uses the brand color exactly as chosen. When it's too light to read on the page background, Theme Studio lists each failing pair with its contrast and refuses to save, and studio-api refuses it too. The dark scheme, the brand surfaces and every text color are generated to pass.

**Rejected.** Darkening the brand color behind the person's back, which changes the brand without saying so.

**Consequences.** A pale brand color, such as a light yellow, needs a darker shade for the site. The person sees why and chooses it.

## 068 — Released versions' changed screenshots are logged and shown to their sites [#decision-068]

**Context.** A dependency upgrade or a change to shared code, such as the field components or Tailwind, can change how a released block version looks on live sites. The design asked for a reviewed screenshot update that's recorded in the audit log and announced to site admins. The browser suite only compared the editor canvas with `sites`, so nothing noticed such a change, and the audit log arrives in checkpoint 10.

**Decision.** The browser suite keeps a baseline screenshot of every fixture of every block version, in light and dark. A released version's baselines change only with a new entry in `packages/blocks/src/rendering-changes.json` that names the version, says what changed and gives the date, and the released blocks check fails a change without one. Each site's Blocks screen shows the entries for the versions it uses. Recording these changes in the audit log comes with the audit log in checkpoint 10.

**Consequences.** An accepted change to a live site's look is a reviewed commit with its reason, and the sites it reaches hear about it. Baselines are rendered on the platform the browser suite runs on.

## 067 — A new draft offers every block in the library [#decision-067]

**Context.** A draft can use only the block types its lockfile pins, and the lockfile changes only through upgrades and merges. A site that started before a block existed could never use it.

**Decision.** A new draft takes the live release's lockfile and adds every block type it doesn't pin, at that type's newest version. Types already pinned keep their versions.

**Consequences.** A type no page uses changes nothing a site shows, so adding it needs no review. New blocks reach every site with its next draft, and other drafts take them when they merge a release that has them.

## 066 — Brand revisions reach sites through SiteDoc, and the scheduled job catches misses [#decision-066]

**Context.** Saving a brand's look makes a revision in D1 and must bring a Brand update draft to every site in the brand. D1 and each site's `SiteDoc` can't share a transaction, so a save could reach some sites and not others.

**Decision.** studio-api records the revision, then asks each site's `SiteDoc` to take it. `SiteDoc` moves its open Brand update draft to the revision, or makes one from what's live, and records the newest revision it has taken, which its outbox copies to D1. Taking a revision again, or an older one, changes nothing. The scheduled job offers each brand's newest revision again to any site whose copy is behind. A newer revision moving a Brand update draft that's under review counts as an edit after submitting, so the draft stays open with it when the older submission publishes.

**Consequences.** A save that couldn't reach a site still reaches it within one run of the scheduled job. Closing a Brand update draft without publishing leaves the site on its older revision until the next save.

## 065 — A draft's brand pin carries the revision, and merges keep the newer one [#decision-065]

**Context.** [Decision 019](#decision-019) has each draft pin a brand revision. Pinning only the revision's ID would make every render, freeze and preview read the revision from D1.

**Decision.** A draft and a snapshot carry the whole revision they pin: the brand, its number, the resolved theme and the identity. Revisions never change, so the copy can't go stale. A merge keeps whichever side has the newer revision and reports it as a change; it's never a conflict, because sites only move forward through their brand's revisions. A restored release takes the live site's revision.

**Consequences.** `SiteDoc`, `sites` and the editor render from the draft or snapshot alone. A palette generator fix changes only revisions saved after it.

## 064 — Theme fonts are static assets of each app [#decision-064]

**Context.** The design self-hosted theme fonts from R2. Serving them from R2 needs an upload step at deploy, a Worker invocation per font request in `sites`, and a route through `studio-api` for the editor canvas and previews.

**Decision.** Fonts come from their Fontsource packages, and a Vite plugin in `@repo/tokens` serves them at `/_fonts/` in development and emits them as static assets of `sites` and Studio in a build. The theme names fonts from a curated list, and the theme CSS declares their faces from `/_fonts/`.

**Rejected.** Fonts in R2, served by each Worker.

**Consequences.** Cloudflare serves fonts without running a Worker, and the canvas and previews load them from Studio's own origin. Fonts are shared code: a font package upgrade reaches live sites like any other, under the same screenshot checks.

## 063 — Lockfiles pin version numbers; a released folder is one on the base branch [#decision-063]

**Context.** [Decision 006](#decision-006) gave each released version an opaque ID for lockfiles to record. Versions are numbered per block and never reused, so `hero@2` already names one folder of code for good, and an opaque ID would add a mapping every lockfile read, migration chain and comparison of versions goes through. What keeps a pin safe is that a released folder never changes, which an ID doesn't enforce.

**Decision.** Lockfiles pin version numbers. A version is released once its folder is on the base branch. A CI check fails a change that edits, adds or removes a file in a released version's folder, unless the whole folder goes, which is how the platform team removes a version nothing uses any more.

**Rejected.** Opaque IDs per released version.

**Consequences.** Ordering versions, for migration chains and merges, is comparing numbers. Within a pull request a new version can still change until it merges.

## 062 — The agent's evals run on demand, never as routine [#decision-062]

**Context.** The design ran the eval suite in CI whenever prompts, models or block contracts changed. Every run calls the model through AI Gateway, so every run costs money, and a change to any block would start one.

**Decision.** The evals stay in `packages/agent/evals` and run only when someone starts them: with `pnpm --filter @repo/agent evals`, or the `Agent evals` workflow run by hand. `pnpm test` doesn't include them, and the browser test that has the agent edit a draft runs only with `PAKSHI_AGENT_TESTS=1`.

**Consequences.** Checking the agent against the real model is a deliberate step after changing its prompts, tools or models, not a gate every change passes.

## 061 — One conversation per person per draft [#decision-061]

**Context.** A conversation belongs to one person and works in one draft. The design had `studio-api` check that the signed-in person owns the conversation they connect to, which needs a record of owners.

**Decision.** A `SiteAgent` is named by its site, draft and person. `studio-api` builds the name from the session, so a connection can only reach the signed-in person's own conversation. The chat panel can clear the conversation to start again.

**Rejected.** Several conversations per draft, with an owners table in D1 and a conversation list in the chat panel.

**Consequences.** There's nothing to check or store about ownership. Two people in one draft each talk to their own agent, and both agents' edits reach everyone through `SiteDoc`.

## 060 — The agent proposes a site plan with a tool, and the plan becomes its brief [#decision-060]

**Context.** To build a site, the agent proposes a plan and the person confirms it before anything is built. The tool list had only `ask_user`, which offers choices but can't show a plan's structure. The context prefix carries the agent's working brief, but no tool wrote one.

**Decision.** A `propose_plan` tool takes the plan: pages with their address and recipe, and each page's sections with a line on what each is for. Chat shows it as a plan card, and the person builds it or asks for changes. The plan they build becomes the working brief, which the context prefix carries into every later turn.

**Consequences.** The plan is data the agent builds from section by section, and a later turn still knows what was agreed.

## 059 — One spend limit on AI Gateway for the whole product [#decision-059]

**Context.** [Decision 008](#decision-008) set a monthly spend limit per brand. AI Gateway's spend limits belong to a gateway, and nothing in the product needs brands to have budgets of their own.

**Decision.** One spend limit on the AI Gateway caps model spend for the whole product. Every request is still tagged with its brand, site and person for cost tracking. When the gateway refuses a request because the limit is reached, the agent tells the person it can't help right now.

**Rejected.** A spend ledger per brand in D1, checked before each model call.

**Consequences.** There are no budgets to configure or record per brand. The limit is enforced by the gateway, which may let a burst go slightly over.

## 058 — The agent runs on Effect AI in a PartyServer Durable Object [#decision-058]

**Context.** [Decision 008](#decision-008) chose `AIChatAgent` from `@cloudflare/ai-chat`. Its current version brings the AI SDK, zod and three MCP packages, a second schema stack beside Effect Schema. By default its protocol stores the history, tool results, approvals, clears and state a client sends, and it serves the history without an access check, so `studio-api` would have to override most of it. The chat panel needs its own interface for plans, questions and each turn's changes either way.

**Decision.** `SiteAgent` is a PartyServer room, like `SiteDoc`. Its turns run on Effect AI's `LanguageModel`, `Chat` and `Toolkit`, with every tool's input and output an Effect schema. Models are reached through the Workers AI binding and AI Gateway with Effect's OpenAI-compatible provider. The chat protocol is a schema in `@repo/contracts`, like live editing's: a connection catches up on the conversation when it opens and follows each turn as it streams, and a client sends only its own messages and answers.

**Rejected.** `AIChatAgent` with its client protocol overridden.

**Consequences.** One schema stack, and the agent's turns run in Node for tests and evals. Pakshi stores the conversation and streams turns itself. A turn cut off because the Durable Object was evicted ends as interrupted instead of resuming, and what it committed stays in the draft, where it can be undone. Workers AI streams OpenAI's format with null fields and a trailing usage event that the provider's parser rejects, so Pakshi's adapter rewrites the stream into strict OpenAI chunks.

## 057 — One turn orders every change to submissions and the live release [#decision-057]

**Context.** The design had publishing check again, after its R2 writes, that the submission was still fully approved and based on the live release, because a Durable Object serves other requests while it waits on R2. `SiteDoc` already runs publishing, rollback and updates in its release turn, one at a time, while edits carry on in its storage turn.

**Decision.** Submitting, deciding on a submission, publishing, rolling back, updating a draft and closing a draft all hold the release turn. Nothing else changes a submission or the live release, so neither can change while `SiteDoc` waits on R2, and publishing needs no second check.

**Consequences.** Two final approvals, or two publishes, happen one after the other, and the second sees what the first did. Edits never wait for a publish.

## 056 — A submission whose merge needs a person goes back to its draft [#decision-056]

**Context.** When another draft publishes during review, `SiteDoc` merges each submission under review. A clean merge keeps its approvals. A merge with conflicts needs a person, but a submission is frozen, and the draft already has an update screen for settling conflicts.

**Decision.** A submission whose merge has conflicts closes as needing an update, and its submitter is told. They update the draft on its update screen and submit again, which starts the workflow from its first step.

**Rejected.** Settling conflicts on the submission itself, which needs a second update screen and a way to edit something frozen.

**Consequences.** Conflicts are settled in one place. A submission is either current with the live release or closed.

## 055 — A draft's sharing lives with the draft in SiteDoc [#decision-055]

**Context.** The design kept draft shares in D1. `SiteDoc` checks sharing for every preview request and every live connection a share allows, and closing a draft should end its sharing at the same moment.

**Decision.** `SiteDoc` stores each draft's sharing with the draft: the people it's shared with, and its general access, each with view or edit access. The outbox copies the people a draft is shared with to D1, for the "Shared with you" list.

**Rejected.** Shares in D1 with `SiteDoc` told of each change, which keeps two stores in agreement.

**Consequences.** Access checks read `SiteDoc`'s own storage. The D1 copy can lag by seconds, and only lists read it.

## 054 — Studio serves previews from the draft itself [#decision-054]

**Context.** The design served previews from `sites` on a preview domain of their own. Studio checked access and redirected with a signed token, `sites` swapped the token for a cookie, and an access counter in the preview's R2 object revoked old cookies. The preview host had to send people without a cookie to Studio, and Studio had to send them to the preview host, so each Worker needed the other's address. Locally, Workers get their ports when they start, so neither address exists before the other deploys. Most people who open a preview have Studio accounts, and the rest open a draft shared with anyone who has the link.

**Decision.** Studio serves a draft's preview at `/preview/{site}/{draft}/{page path}`. On every request, `SiteDoc` checks the draft's sharing against the person viewing, or against an anonymous visitor, and returns the page from the draft's latest saved state. Studio renders it with the same block components and theme CSS as `sites` and the editor canvas. The random draft ID keeps the address unguessable.

**Rejected.** A preview host with tokens, cookies and an access counter; previews on each site's own domain, which needs DNS and a certificate there for every preview.

**Consequences.** There is no preview domain, token, cookie, access counter or preview snapshot in R2. Revoking access blocks the next request, and a preview never lags the draft. Draft content renders on Studio's origin, as it already does in the editor canvas, which is safe because editors can't add HTML, scripts or unsafe links. Studio's preview is one more renderer, so it has its own screenshot checks against `sites`.

## 053 — Drafts behind the live site merge on their own when no one needs to decide [#decision-053]

**Context.** The design requires a behind draft to be updated the next time someone opens it and before it's submitted. The Studio designs show an update screen for settling conflicts, but most merges have none, and sending people through a screen with nothing to decide adds a step for nothing.

**Decision.** Opening a behind draft in the editor, or publishing it, merges the live release in when the merge has no conflicts, and carries on. Only a merge with conflicts sends the person to the update screen. The drafts list and the editor show a draft as behind until then.

**Consequences.** Two publishes started at once both succeed, one after the other, when they don't conflict. The update screen is always a screen with decisions on it.

## 052 — Publishing's production checks move to checkpoint 9, with domains [#decision-052]

**Context.** Checkpoint 5 asked that a publish and a rollback be live on a production platform subdomain within 60 seconds, and that no cached page link to CSS or JavaScript a `sites` deploy removed. There's no production stack yet, and nothing builds the platform subdomain. The page cache works only on a custom domain ([decision 027](#decision-027)), and dev serves `sites` through Vite, so there's no deploy to observe locally either.

**Decision.** Both checks move to checkpoint 9, which builds custom domains and the platform subdomain and needs production anyway. Checkpoint 5 proves in the dev stack that the next request serves a new release, and the page cache key already holds the release and the Worker version.

**Consequences.** Nothing in checkpoint 5 has run against Cloudflare's network. Checkpoint 9 sets up production before its own checks.

## 051 — The outbox copies to D1 only what something reads [#decision-051]

**Context.** The design has `SiteDoc` keep the page and draft index and audit entries in D1 through its outbox. In checkpoint 5 the reconcile job reads release rows, and nothing yet reads the index or the audit log.

**Decision.** The outbox is a general queue of copies, written in the same transaction as the change and delivered by the alarm. For now it carries release rows. The page and draft index arrive with the dashboards that read them, and audit entries with the audit log in checkpoint 10.

**Consequences.** D1 holds every site's releases, which the reconcile job compares with KV.

## 050 — A site's first release is the one KV serves [#decision-050]

**Context.** `SiteDoc` becomes the source of truth for the live release and the only writer of KV's `site → release` entry. Non-production stages seed their sites by writing snapshots and KV directly, at deploy time, where no Durable Object can be reached.

**Decision.** A `SiteDoc` that has recorded no release takes the one KV serves as its first, recorded as imported, and owns the site's live release from then on.

**Rejected.** A non-production studio-api route that publishes the seed through `SiteDoc`, which needs studio-api reachable from the deploy-time seed.

**Consequences.** On a running dev stack whose `SiteDoc`s have started, a changed fixture reaches its site only after `pnpm dev:destroy`, since the reconcile job puts KV back to what `SiteDoc` recorded. Test stages are fresh each time.

## 049 — Items in lists and menus merge by ID, and clashing addresses are conflicts [#decision-049]

**Context.** The design merges by block ID and field. A gallery's images or a menu's links are one field, so two people changing different images would conflict. And a merge of two valid sides can still be invalid: a page added on each side can take the same address.

**Decision.** Lists inside props and menus merge item by item and field by field, with the same ordering rules as blocks; anything that conflicts inside a list makes the whole list the conflict. Two pages that end up with one address are a conflict, where keeping one side's page removes the other's from the draft. Every conflict has a key naming what it's about, so a side chosen for it still applies when the merge is worked out again after more edits.

**Consequences.** Merges need a person less often, and a merged draft is always one `applyOps` accepts.

## 048 — A rollback is a release of the snapshot that was live before [#decision-048]

**Context.** Rollback makes the release before the latest publish live again. The Releases screen in the Studio designs lists a rollback as its own entry, with who did it and when, and offers no rollback of a rollback.

**Decision.** Rolling back records a new release of the snapshot that was live before the latest publish, naming the publish it undid. Only a publish can be rolled back, so a rollback can't be repeated to walk further back.

**Consequences.** A site's history is one list of releases, the latest live. Drafts that started from the rolled-back release are behind, like after any publish.

## 047 — A merge commits as a batch of ops, led by a system-only rebase [#decision-047]

**Context.** People may be editing a draft while it's updated, so a merge has to reach their editors, the batch log and the `writes` table like any change. Ops cover pages and blocks, but not the draft's base release, lockfile, theme, settings, forms or menus, which only a merge changes so far.

**Decision.** A merge's result becomes one batch of ordinary ops against the draft, led by a `rebase` op that moves the draft onto the release and sets those site-wide values. Only `SiteDoc` makes one: a person's batch that carries it is refused. Publishing a draft that someone edited meanwhile commits a `rebase` too, so the draft starts from the release it just became. An editor that receives a merge to block versions it didn't load asks the person to open the draft again. When menus get their editing screen in checkpoint 9, they get ops of their own and leave `rebase`.

**Rejected.** Replacing the draft wholesale, which would lose who wrote each part, and with it undo's rule and the notices when a change is replaced.

**Consequences.** Broadcast, catch-up, undo and history need nothing new for merges, and someone whose field a merge replaces is told.

## 046 — Someone typing in a replaced field is told when they stop [#decision-046]

**Context.** The later write to a field wins, and its earlier writer is told. When two people type in one field, each batch replaces the other person's, several times a second. A notice for each would be noise, but staying quiet while someone types left whoever stopped second never knowing they'd lost.

**Decision.** A person whose write is replaced is told at once, unless they have an unconfirmed write to that field, which will replace it in turn. Only writes made since they opened the editor count: `SiteDoc` remembers every writer, but a change to something they wrote on an earlier visit isn't news to them. If they're still typing in the field, the notice waits until they stop, and is dropped if they type over the replacement, because then the other person is told.

**Consequences.** Whoever ends up replaced hears it once. The typing marker in presence remains the way people avoid typing in one field together.

## 045 — Remote changes wait for composition, and the canvas keeps the view in place [#decision-045]

**Context.** The editor spec's rules say nothing is written into a field while an input method composes, and the change applies when composition ends. A field's value is replaced whole, so applying the stored value then would drop what was composed, and saving the composed value would drop the change. The rules also say the view stays put when content grows above it. Chrome anchors scrolling on its own and Safari doesn't, so a test in Chrome passed without the editor doing anything.

**Decision.** During composition a field saves nothing and takes no remote change. When it ends, a change that arrived meanwhile is made again around what was composed: in plain text by moving the composed splice onto the new value, in rich text by mapping the change's steps through the composition's own. The result is saved as the person's edit. The canvas turns the browser's scroll anchoring off, and before each remote change notes the focused element or the first field or block in view, then scrolls by however far it moved. Settings panel text inputs are uncontrolled, like the canvas's fields, so a remote change keeps their caret too.

**Consequences.** Every browser behaves the same, and each rule has a browser test that fails without it.

## 044 — Studio forwards live connections before TanStack Start [#decision-044]

**Context.** The design passes Studio's WebSocket to `studio-api` over the service binding, which Cloudflare doesn't document. TanStack Start's request handling serves pages and server functions, and runs its responses through its own middleware.

**Decision.** Studio's server entry, `apps/studio/src/server.ts`, sends `/api/live/{site}` to `studio-api` unchanged, before TanStack Start sees it. `studio-api` refuses a connection from another origin, checks the session and `page.edit`, and passes the socket to the site's `SiteDoc` with the person and their permissions in a header it sets itself, replacing any the browser sent.

**Consequences.** The passthrough works in the dev stack's local runtime, from the browser through both Workers to `SiteDoc`. The agent's chat panel in checkpoint 7 can take the same route.

## 043 — Live connections catch up from the batch log [#decision-043]

**Context.** [Decision 032](#decision-032) sent one batch at a time over RPC until live co-editing. A live connection drops and comes back, and the editor must neither miss a batch nor apply one twice.

**Decision.** The editor still opens a draft from Studio RPC. Every connection then starts with Sync and the editor's revision, and `SiteDoc` answers with the batches committed since, from its batch log, or with the whole draft when the editor is more than 500 batches behind. The editor sends every batch `SiteDoc` hasn't confirmed, in order, without waiting on each, and sends them again on each new connection; `SiteDoc` answers a batch it already committed with Known. Broadcasts carry revisions, so the editor skips one it has and asks for a sync after a gap. `SiteDoc` handles live messages and commits one at a time, so each commit's broadcast leaves before the next commit. Studio's page list still commits over RPC, and `SiteDoc` broadcasts those commits too.

**Rejected.** Sending the whole draft on every connection, which grows with the site; letting PartySocket buffer messages while closed, which would send them a second time after the editor's own resend.

**Consequences.** A property test with three editors making random edits, undos and reconnects ends with every editor showing `SiteDoc`'s draft.

## 042 — Undo passes over parts someone else wrote since [#decision-042]

**Context.** [Decision 033](#decision-033) left the undo rule for live co-editing: an undo applies only where its author's write is still the latest. `SiteDoc` has to know that for every field and block an undo touches, including after it restarts.

**Decision.** `SiteDoc` keeps the latest writer of each part of a draft in a `writes` table, written in the same transaction as the batch. A part is a field or a part of one, a block's variant, surface or place, a whole block with its items, or a page's meta field, address or whole page. A write replaces the records below its part. An undo batch is marked as one, and `SiteDoc` applies each of its ops whose part is still its author's latest and still exists, and passes over the rest. Redo goes the same way. The broadcast carries the ops that applied, the positions of those passed over, and the people whose writes a value change replaced, who are told. The rule is the document module's `commitBatch`, which the editor's tests run too.

**Consequences.** Undo never erases someone else's change, and says what it left. The table grows with the parts of a draft, not with its history.

## 041 — Permission changes reach live connections with the permissions screens [#decision-041]

**Context.** Checkpoint 4 asked that removing a person's permission stop their next batch. Nothing changes a grant until the permissions screens in checkpoint 10, so the code that tells `SiteDoc` about a change would have no caller.

**Decision.** `studio-api` finds the person's permissions on the site when it opens their live connection. `SiteDoc` keeps them on the connection and checks every batch against them, with no D1 read. Checkpoint 10's grant and override changes tell the `SiteDoc`s they affect to reload them, and its checks include a removed permission stopping the next batch.

**Consequences.** Until checkpoint 10, a permission removed while someone is connected lasts until their connection reopens.

**Amended** by [decision 080](#decision-080): `SiteDoc` keeps each person's permissions in its storage rather than on each connection, so the agent's batches are checked too.

## 040 — Dragging is for pointers; the keyboard moves blocks with commands [#decision-040]

**Context.** The editor spec lists keyboard dragging as dnd-kit's job and names "dropping the keyboard" as a mistake Puck made. dnd-kit 0.5's keyboard sensor moves a plain draggable 10 pixels per arrow press, and its accessibility plugin announces raw IDs and puts its description element in Studio's document, where a handle inside the canvas can't reference it. Meanwhile, move up, move down and move to already reach every spot a drag can, from the keyboard, the outline and the block menu.

**Decision.** Drag handles take the pointer sensor only, with a 4-pixel distance so a click stays a click. They are hidden from assistive technology and left out of the tab order. The keyboard moves blocks with the move commands, and each move is announced with where the block landed. A drop runs the `place` command, whose moveBlock comes from the same `moveOp` the move commands use.

**Rejected.** dnd-kit's keyboard sensor with a plugin that jumps between drop spots, which would be a second keyboard path to the same moves; dnd-kit's accessibility plugin.

**Consequences.** Puck's mistake was offering no keyboard path at all. Here every drag has a command, as WCAG 2.5.7 asks, and a drag and the matching command produce the same ops.

## 039 — The picker previews one block, and layouts are chosen from the block's own content [#decision-039]

**Context.** The editor spec asked for a thumbnail per block in the picker, rendered from a fixture, and for variants and surfaces chosen from previews. A thumbnail small enough for a grid of a dozen blocks can't be read, and each rendered thumbnail is a frame of its own.

**Decision.** The picker lists blocks by name, with search, and previews the highlighted one in the draft's theme with the placeholder content it will start with. The settings panel renders the selected block's own content in each of its layouts, and shows each background as a swatch of the theme's colors for that surface. Layout previews follow the block's content once typing pauses, so a keystroke never renders them.

**Consequences.** A person sees exactly what they'll get before choosing. The picker renders one preview frame, and the settings panel one per layout.

**Amended** by [decision 088](#decision-088): Studio's block gallery shows every block as a live preview of its sample, which renders only as it comes near the viewport.

## 038 — Items move up and down across sections [#decision-038]

**Context.** The editor spec listed four move commands: up, down, into the previous section, and out to the top level. Placement rules make the last two impossible: items go only in a slot that accepts them, and sections only at the top level.

**Decision.** Move up and move down move a block one place in its list. An item at either end of its slot moves into the nearest slot before or after it that accepts it, even in another section. Move to puts an item at the end of any other slot that accepts it. The header and footer belong to every page, so they don't move.

**Consequences.** A keyboard user can take an item anywhere it's allowed with two commands, and no command is ever offered that placement rules would refuse.

## 037 — A placeholder is a block's own starting content, found by its value [#decision-037]

**Context.** The editor spec gives every block placeholder content for a new instance, and the checks block a submission while any placeholder remains, but nothing defined what a placeholder is. An empty required field can't be one: a draft always holds required fields, and an image, a form or a link has no empty value. A new block should also look finished, not like a form waiting to be filled in.

**Decision.** Every section and item version ships a `fixtures/placeholder.json`, which `defineBlock` decodes into its contract. It uses built-in images and a contact form that every site resolves through `siteData`. `placeholderPaths` finds the fields still holding placeholder content: a built-in image or form, a button whose link is unchanged, or text, rich text or a link equal to a placeholder of that block type, including the items in a section's placeholder. A button's label alone doesn't count, because short labels such as "Get started" are often real.

**Rejected.** Empty required fields as placeholders, which would let drafts lack required values; a marker in the document, which every op, undo and merge would have to carry.

**Consequences.** The document gains no field, and a placeholder stops being one the moment its value changes. The placeholder is a fixture, so the screenshot and axe gates cover it. When the agent lacks content ([decision 026](#decision-026)), it can leave a block's placeholder values in place, and pre-flight finds them the same way.

## 036 — The canvas fixes the theme's color scheme instead of following the system [#decision-036]

**Context.** Sites follow the visitor's color scheme through `prefers-color-scheme`, and the editor lets a person switch the canvas between light and dark. The editor spec asked for the frame's `color-scheme` to do this, but a frame's `prefers-color-scheme` follows the operating system in Chromium, not the frame element's `color-scheme`.

**Decision.** `themeCss` takes an optional scheme. Without one it writes both schemes behind the media query, as sites need; with one it writes only that scheme's variables. The canvas passes the scheme the person chose.

**Consequences.** Both schemes of a theme render from the same variables in both places, and the canvas-versus-sites screenshot checks compare them in each scheme.

## 035 — Tailwind's spacing scale counts as a theme token in blocks [#decision-035]

**Context.** Blocks may use theme tokens only, and a lint rule rejects "literal colors, fonts or spacing". Read strictly, that forbids `gap-6`, and blocks couldn't lay themselves out. But `--spacing` comes from the theme's density, so every step of Tailwind's spacing scale already moves with the theme.

**Decision.** `pakshi/no-literal-styles` rejects arbitrary values for colors, fonts and spacing, Tailwind's own palette colors, font families other than the theme's, and inline styles. It allows the spacing scale and layout utilities such as aspect ratios. Which classes bypass the theme is decided in `@repo/tokens`.

**Consequences.** A block can't hard-code a look, and a density change still respaces every block.

## 034 — Islands and media upload wait for the checkpoints that need them [#decision-034]

**Context.** Checkpoint 2 adds a gallery and a form block, and the editor spec's media popover offers uploads. No checkpoint builds Astro's island map, a form posts as plain HTML without it, and uploads belong with the media library and Cloudflare Images in checkpoint 9.

**Decision.** Gallery v1 is a static grid with no lightbox, and the form block renders a plain HTML form through a shared `FormView` component, so how forms post can change without a new block version. The media popover chooses from the site's and brand's libraries and edits alt text; uploading arrives with the media library.

**Consequences.** Nothing hydrates on sites yet. The first interactive block builds the island map, and a lightbox arrives as a new gallery version.

## 033 — A draft's history is its batch log until something reads more [#decision-033]

**Context.** The technical design records one revision per editing session or agent turn, with a full checkpoint every so often. Nothing reads them before the audit log, restore and agent-turn undo, and SiteDoc needs a record of committed batches anyway, to apply a batch sent twice only once.

**Decision.** SiteDoc stores every committed batch with its actor, time, revision, ops and inverse ops. Grouping into sessions and full checkpoints wait until a feature reads them. Undo sends a command's inverse ops as an ordinary batch; the rule that skips fields someone else changed since arrives with live co-editing, which has the test for it.

**Consequences.** Sessions and turns can be derived from the log later without a migration.

## 032 — The editor sends batches over RPC until live co-editing [#decision-032]

**Context.** Checkpoint 4 connects Studio to SiteDoc over PartySocket. Checkpoint 2 has one person editing, so the WebSocket's broadcast and presence have nothing to do yet.

**Decision.** The editor sends batches through a `Connection` with one method, `send`. Studio implements it with the `applyBatch` server function, which calls `StudioRpcs.applyBatch`, and studio-api calls the site's SiteDoc. The editor sends one batch at a time and resends one that didn't arrive with the same ID.

**Consequences.** Each batch checks the session and reads the person's grants from D1, which the WebSocket's per-connection permission cache replaces in checkpoint 4. Only the `Connection` implementation changes then.

## 031 — Ops name their page, and cover variants, surfaces and addresses [#decision-031]

**Context.** The op vocabulary addressed a block by ID alone, but each draft page is its own SQLite row, so SiteDoc would need an index from block to page. The editor also needs to change a block's variant and surface, and renaming a page can change its address, and no op did either.

**Decision.** Block ops name their target: a page, or `site` for the header and footer. Structure ops name their page. `setVariant`, `setSurface` and `setPath` join the vocabulary, and `setPath` refuses an address another page has.

**Consequences.** An op touches exactly one row, and merging, undo and the agent use the same ops.

## 030 — Alt text belongs to where an image is placed [#decision-030]

**Context.** The snapshot manifest stored alt text on the media file, and the media popover edits it. Editing a shared library record would change every draft at once, outside any draft or approval. Alt text also depends on context: the same photo can say something in one place and be decoration in another, which the check for alt text on every meaningful image needs to know.

**Decision.** A media reference in props carries its own `alt`. An empty alt marks an image as decorative; a missing one is incomplete, which freezing checks. The library keeps an alt text per image only as the suggestion for new placements.

**Consequences.** Alt text changes through drafts and approvals like any other content, and merges field by field.

## 029 — Studio calls studio-api through an Effect RPC contract [#decision-029]

**Context.** Studio called a method on `studio-api`'s entrypoint class over native Workers RPC. The contract was that class's TypeScript type, so nothing checked calls at runtime, failures reached Studio untyped with no timeout, and every method took the session cookie as an argument. `studio-api` must stay a plain Worker, because PartyServer and `AIChatAgent` need plain Durable Object classes, so Alchemy's Effect Worker RPC doesn't apply.

**Decision.** Each API boundary is an Effect `RpcGroup` in `packages/contracts`, with payload, success and error schemas for every method. `studio-api` serves `StudioRpcs` from a named `StudioRpc` entrypoint, over Effect RPC's HTTP protocol. Studio calls it through one helper that sends the session cookie and Studio's origin as headers, applies a timeout, stops when the browser request is cancelled, and turns every failure into a user-safe error in one place. A `StudioSession` middleware on the contract checks the session and provides the signed-in person to handlers; a missing session is the typed `Unauthenticated` error. Sign-in stays plain HTTP over the default entrypoint.

**Rejected.** Native Workers RPC with a TypeScript interface, which has no runtime checks or typed errors; Alchemy's Effect Worker class, which can't host PartyServer's Durable Objects.

**Consequences.** A new Studio feature adds one `Rpc.make` to the contract and one handler, and gets validation, the session check, the timeout and error mapping with it. Each call pays for JSON encoding and an internal HTTP hop, and the transport uses `effect/unstable/rpc`, which may change before Effect 4 is released.

## 028 — Two stacks, dev and prod, and destroying one deletes everything [#decision-028]

**Context.** The design had branch, staging and production stages, retained production's D1 databases and R2 buckets on removal, and failed CI on any production plan that deleted a database, a bucket or a Durable Object class. That meant another account to run, and teardown that left data behind.

**Decision.** Pakshi has two stacks: `dev`, which runs locally, and `prod`. `dev:destroy` and `prod:destroy` delete everything in the stack, Durable Object data and the R2 bucket's contents included. Test suites deploy throwaway local stages. Checks that need Cloudflare's network run against production.

**Rejected.** A staging stage; retaining production stores on removal; a CI check on the production plan.

**Consequences.** Nothing stands between a destroy, a removed resource or a renamed Durable Object binding and production data. Recovery relies on D1 Time Travel and Durable Object point-in-time recovery within their 30-day windows, and a destroyed stack can't be recovered that way.

## 027 — Serve sites through Alchemy's Astro adapter, with lookup and cache in middleware [#decision-027]

**Context.** The design named `@astrojs/cloudflare`. Alchemy's `Website.Astro` resource, which builds, emulates and deploys the `sites` Worker, adds its own fork of that adapter, fails the build if the app declares one, and owns the Worker's entry file. `sites` has to look up the host and release in KV and serve pages from the Workers Cache API before Astro renders.

**Decision.** `sites` uses Alchemy's Astro resource and adapter. The host → site → release lookup, the page cache and media serving run in Astro middleware, which sees every request after static assets. The cache key is the release ID, the Worker version and the path, as before.

**Rejected.** Building with the upstream adapter and deploying the output as a plain Worker, which gives up Alchemy's local emulation and build memoization for `sites`; a separate front Worker for caching, which adds a fifth Worker; Cloudflare's newer Workers Caching and Astro 7's route cache built on it, whose cache key leaves out the hostname, so one Worker serving many sites would need a gateway Worker to tell them apart, and Alchemy's adapter turns Astro's cache provider off.

**Consequences.** `sites` has no Worker entry of its own, so anything that must run before Astro goes in middleware. The Cache API does nothing on `workers.dev` hostnames, so deployed pages are cached only once `sites` serves a custom domain; the dev stack emulates the cache locally. The key starts with the site, and only GET and HEAD requests use the cache.

## 026 — Drafts may be incomplete; completeness is checked at submission [#decision-026]

**Context.** `SiteDoc` validated every batch against the full block schema. A heading with a 3-character minimum could then never be cleared to retype it, and a person couldn't leave a required field empty while working on the rest of a page.

**Decision.** People's batches are checked for types, integrity, link rules and the limits the editor enforces while typing: maximum lengths, allowed marks and nodes, variants and surfaces. Completeness (required fields and minimum lengths) is checked when a draft is frozen, and the checks list what's missing. The agent's batches are also checked for completeness, so it gets a structured error instead of leaving a field empty; where it lacks content it writes a placeholder, which pre-flight also blocks.

**Rejected.** Full validation on every batch, which blocks ordinary editing; keeping a separate unsaved value in the editor until a field is valid, which is a second copy of the page that other people and the agent can't see.

**Consequences.** A draft can hold incomplete blocks, and the editor marks them. Nothing incomplete can be submitted or published, because freezing checks the full contract.

## 025 — Build our own visual editor on the page document, instead of Puck [#decision-025]

**Context.** [Decision 013](#decision-013) kept Puck and added a sync module. That meant a two-way adapter to Puck's tree, converting Puck's HTML rich text to TipTap JSON, translating our ID-based ops into Puck's index-based actions, taking over its undo, and working around seven known gaps, with a full reload when a client fell out of step. All of it existed because Puck keeps its own copy of the page. A source review of Puck 0.23 found 23,769 lines of TypeScript, about 5,400 of them for drag and drop into arbitrarily nested zones, which Pakshi's two-level documents don't need. It also found no collaboration support, and focused fields that overwrite remote changes. EmDash and Payload have no on-page structure editing or live collaboration to adopt instead.

**Options.** (a) Puck with a sync module ([013](#decision-013)). (b) A fork of Puck. (c) Our own editor on our page document, using TipTap for rich text fields, dnd-kit for drag and drop, and shadcn/ui for controls. (d) A ProseMirror document for the whole page, with sections as nodes.

**Decision.** (c). `@repo/editor` in `packages/editor`, specified on the [Editor](/editor) page. It renders the page into a same-origin iframe with the same components and CSS as `sites`, and it keeps a local copy of the draft in step with `SiteDoc` by running the same document module. Blocks render their fields through field components from `packages/blocks`, which output plain markup on the site and editable markup in the editor. The editor also needs four changes elsewhere:

- `applyOps`, validation and inverse ops form a document module in `packages/domain` that imports no server code, so the browser can run it.
- Batches, new blocks and new list items carry IDs their sender creates, so a batch sent twice has no extra effect.
- Lists inside props carry item IDs, and paths address items by ID.
- Undo is per command: an undo batch applies only to fields where its author's write is still the latest.

**Rejected.** (a), because the sync module and its gap handling were the riskiest work in Pakshi and would remain a second copy of the page to reconcile. (b), because we would own a 24,000-line codebase built around index addressing. (d), because ProseMirror addresses content by position and its collaboration model needs a server that rejects stale versions, so we'd need the adapter again, and `SiteDoc` orders batches with last-write-wins per field instead. Dragging blocks from a palette into the canvas, because a "+" at each insertion point does the same job without cross-frame dragging.

**Consequences.** No adapter, no rich text conversion and no reload to recover from drift. We own the canvas, overlays, drag-and-drop behaviour and keyboard support, and the [build plan](/build-plan#2-editing-content) gives the editor two checkpoints before live co-editing. The field components become part of every frozen block version, so their contract must stay small and stable.

## 024 — The site's Durable Object owns approvals and publishing [#decision-024]

**Context.** Approval progress lived in D1 while the snapshot being approved, merges and the live release lived in `SiteDoc`. An approver could act on a stale D1 view after a merge had restarted the workflow, and two final approvals could both pass the "based on the current live release" check while `SiteDoc` waited on R2.

**Decision.** `SiteDoc` owns submissions and their approval progress, and D1 keeps a copy for dashboards. An approval decision goes to `SiteDoc`, which rejects it if the submission changed since the approver loaded it. Publishing checks approval and the live release again after its last R2 write, then records the new live release. `SiteDoc` is the only writer of the live release to KV; the reconcile job asks it to rewrite and never writes KV itself.

**Consequences.** Approvals, restarts, publishes and rollbacks for a site happen in one order, in one place. The Approvals screen reads a copy that can lag by seconds, but a decision based on it can't take effect if it's stale.

## 023 — One-click rollback undoes only the latest publish [#decision-023]

**Context.** Rolling back to any past release without approval could bring back content that was removed on purpose, such as a page pulled for legal reasons.

**Decision.** One-click rollback, with no approval, undoes the most recent publish and can't be repeated to walk further back. Any older release is restored as a draft, which goes through the site's workflow like any other change.

**Rejected.** Rollback to any release without approval.

**Consequences.** A bad publish is still undone in about a minute. Older content returns only with approval.

## 022 — Each site's submissions in their own Durable Object [#decision-022]

**Context.** One shared D1 `submissions` database, capped at 10 GB, would let a flood on one site's form fill it and break forms on every site. D1 databases can be created through the API, but a Worker reaches D1 only through bindings fixed at deploy time, about 5,000 per Worker, so a database per site would mean a redeploy for every new site or querying through the account API and its rate limit ([D1 limits](https://developers.cloudflare.com/d1/platform/limits/)).

**Decision.** Each site's submissions live in a `SiteSubmissions` Durable Object with SQLite storage, hosted by `sites-api` and bound from `studio-api` for authorized reads. The site's first form post creates it. Form posts over 64 KB are rejected.

**Rejected.** One shared D1 database; a D1 database per site.

**Consequences.** Each site's customer data is isolated, with up to 10 GB and 30-day point-in-time recovery per site, and no provisioning. Nothing can query submissions across sites, which the product doesn't need.

## 021 — No spam protection on forms [#decision-021]

**Context.** The design gave every site its own Turnstile widget, but non-Enterprise accounts are limited to 20 widgets ([plans](https://developers.cloudflare.com/turnstile/plans/)). Honeypots and rate limits add setup and edge cases for little early value.

**Decision.** Forms ship without spam protection. To keep an unprotected form from sending mail to any address a visitor types, forms send no email to submitters; notifications go only to the form's configured addresses.

**Consequences.** Spam can reach a site's submissions until protection is added, but only that site's ([022](#decision-022)). When it is, one widget covers the sites domain and its subdomains, and custom domains are grouped 10 to a widget.

## 020 — Share drafts like documents [#decision-020]

**Context.** People need to show drafts to colleagues and to people outside the organization, and to invite others to edit.

**Decision.** Drafts are shared like documents: with named people, the whole organization, or anyone with the link, and the person sharing chooses view or edit access for each. Every draft has a preview link at an address that can't be guessed, served from a fixed R2 key that each save overwrites; KV is too slow to show the latest save. Editing always needs a signed-in Pakshi user, so a link shared for editing gives everyone else view access. Edit access through a share covers one draft and never includes submitting or publishing.

**Rejected.** Previews visible to signed-in staff only; frozen previews with fixed expiry times.

**Consequences.** A preview lives as long as its draft and always shows its latest saved state. Approvers still review a frozen submission snapshot.

## 019 — Brand changes reach sites as drafts; no brand locks [#decision-019]

**Context.** A brand theme change would otherwise ship with whatever unrelated change a site publishes next. Brand locks, which limit what sites may change, add a validator, hidden controls and agent rules.

**Decision.** Sites use their brand's theme and identity as they are, with no overrides and no locks. Each save of a brand's theme, logo or favicon is an immutable brand revision, and each draft pins one, the way its lockfile pins block versions. A new revision creates a Brand update draft on every site in the brand, or moves an unpublished one forward, and it follows that site's workflow. Other drafts keep their pinned revision until they merge after the update is live. The same mechanism creates block upgrade drafts on every affected site.

**Rejected.** Brand locks and site theme overrides; theme changes that ride along with the next publish.

**Consequences.** A site that needs a different look belongs to a different brand. Locks can be added later if a real need appears.

## 018 — Media files never change [#decision-018]

**Context.** Replacing a file everywhere it's used would change live sites without a publish.

**Decision.** Each upload is a new file with its own ID, and files are never replaced or versioned. A new image appears only where someone swaps it in. The brand logo and favicon are brand settings that point at a file, so changing them reaches sites through Brand update drafts ([019](#decision-019)). A file is kept while any draft or live release uses it, and for 3 months after the last one stops.

**Consequences.** A media ID always renders the same file. Changing a common asset other than the logo or favicon means updating each place it's used.

## 017 — Named drafts that merge like branches [#decision-017]

**Context.** With one shared draft per site, one person's unfinished page blocks another person's urgent fix or ships with it, and a second submission replaces the first.

**Decision.** A site has one live release and any number of named drafts, each starting from a release. Publishing a draft makes it live, and every other draft is then behind. A draft that's behind must be updated the next time it's opened and before it's submitted. Updating is a three-way merge by block ID and field. Different fields, blocks or pages merge automatically; conflicts (same field on both sides, edit against removal, the same list reordered on both sides) need a person, and a model may suggest a merge for text. A submission under review that merges cleanly keeps its approvals; one that needed a person restarts its workflow.

Five rules keep merges safe. All sides are migrated to the newest block version any of them uses before diffing. The merged draft is checked for structure, and a failure is a conflict; the checks run only at submission. A submission publishes only if it's based on the current live release. Publishing closes a draft only if nobody edited it after it was submitted. And people already in a draft that falls behind keep working; the update is required the next time it's opened and before it's submitted.

**Rejected.** One draft per site; publishing chosen pages from a shared draft; a draft per page.

**Consequences.** More to build: a drafts list, the merge engine and a conflict screen. The [build plan](/build-plan#5-publishing-and-merging) proves the merge engine early. Several people can still edit one draft live together ([007](#decision-007)).

## 016 — Keep all site data [#decision-016]

**Context.** Form submissions and past releases are part of a site's data.

**Decision.** Nothing deletes submissions or releases automatically. They are kept for as long as the site exists. A single submission, or everything for one person, can be deleted on request.

**Consequences.** Storage grows over time, which Durable Objects and R2 handle comfortably. An earlier release can come back while its block versions and media are still retained ([006](#decision-006), [018](#decision-018), [023](#decision-023)).

## 015 — Approval workflows on the organization, a brand or a site [#decision-015]

**Context.** Review requirements differ between sites and brands, and the people who own a site know them best.

**Decision.** Workflows can be set on the organization, a brand or a site, and the nearest one applies. A workflow is an ordered list of any number of steps, including none, each naming who can approve (roles or people) and how many approvals it needs. Definitions are rows in D1, and each submission's progress lives in the site's `SiteDoc` ([024](#decision-024)); completing the last step publishes. The workflow editor is a list of steps. A visual, node-based editor built with an off-the-shelf flow library can follow, on the same definitions.

**Rejected.** A fixed cap on approval steps; a general-purpose workflow engine.

**Consequences.** Owners at each level control their own review process without platform changes. Editing a workflow is a permission, so whoever holds it controls how a site publishes.

## 014 — Fine-grained permissions, with roles as bundles and per-person overrides [#decision-014]

**Context.** Brands are just groupings of sites; what people may do must be controlled precisely and the same way everywhere.

**Decision.** Permissions are fine-grained named actions, and they decide what a person can do. Roles are sets of permissions for giving access quickly, with defaults shipped by Pakshi and custom roles created by admins. Grants give a person a role on the organization, a brand or a site, and inherit downward. An override switches one permission on or off for one person on one scope and beats any role. A person can grant only permissions they hold, on scopes they control. One `authorize` function in `packages/domain` is used by the API, the agent's tools, live editing and Studio's UI.

**Consequences.** One place to reason about access. New features add permissions rather than new checks. Rules such as self-approval are permissions, so admins decide them.

## 013 — Integrate Puck through a sync module; don't fork [#decision-013]

**Superseded** by [decision 025](#decision-025): Pakshi builds its own editor.

**Context.** Live collaboration needs Puck to accept changes from others without losing the user's place or undo. Puck has no collaboration support. Its core is about 24,000 lines of TypeScript under the MIT license, built on a zustand store with a reducer of small actions ([source](https://github.com/puckeditor/puck)).

**Options.** (a) Fork Puck. (b) A sync module on Puck's public API, plus patches where the API falls short. (c) Build our own editor.

**Decision.** (b). Puck already exposes what the sync needs: an `onAction` callback for every local change, small actions (insert, move, remove, replace) we can dispatch for remote changes, a flag to keep them out of its history, and lookup by block ID. Puck's actions address blocks by index, so the sync module converts our ID-based ops using that lookup. The biggest gap is undo, which restores whole-page snapshots, erasing other people's changes, and has hard-wired shortcuts. We take the undo shortcuts in capture-phase key listeners and hide Puck's undo buttons, so no patch should be needed; if that proves not to be enough, a pnpm patch replaces its history slice. Smaller gaps, such as fresh IDs on replayed inserts, index-based selection and focused fields that ignore remote changes, are handled in the sync module and proven in the [build plan](/build-plan#4-live-co-editing).

**Rejected.** A fork: we would own drag and drop, the canvas iframe and every field type, and fall behind an actively developed 0.x library. Our own editor: much larger, for no gain.

**Consequences.** We keep Puck's upgrades, and re-check the patch on each one. If the [live co-editing checkpoint](/build-plan#4-live-co-editing) shows the public API can't support live editing well, we revisit a fork with evidence.

## 012 — Effect Schema instead of Zod [#decision-012]

**Context.** The starter defines shared schemas with Effect Schema (Effect v4). The earlier design assumed Zod 4.

**Decision.** Use Effect Schema as the one schema library for pages, blocks, edit operations and agent tools. It produces Standard Schema and JSON Schema, which cover editor control generation and agent tool definitions.

**Consequences.** One schema library and one style across the repo. Libraries that expect Zod specifically (for example some json-render helpers) are used only through JSON Schema, or not at all.

## 011 — Build on application-platform-starter [#decision-011]

**Context.** A starter already exists with a monorepo pattern and utilities for Cloudflare apps ([repo](https://github.com/AdiRishi/application-platform-starter)).

**Decision.** Pakshi starts from it: pnpm and Turborepo, Alchemy for all infrastructure and bindings (instead of Wrangler configs), Effect for application services, oxlint and oxfmt with its lint rules, TypeScript 7, Vitest, Playwright, and Blume docs with repository ADRs. Its `apps/web` becomes `apps/studio`, and `apps/sites` is added for Astro.

**Consequences.** A working foundation from day one. Alchemy is a beta dependency pinned (with a patch) by the starter, so upgrades are deliberate. PartyServer and `AIChatAgent` Durable Objects are plain classes, which a starter-style Effect Worker can't host, so `studio-api` is a plain Worker with its own entry file. Alchemy deletes a Durable Object class's data when the class leaves a Worker, so CI fails if a production plan removes one.

## 010 — Workers Paid plan; no Enterprise features, no root domains [#decision-010]

**Context.** Pakshi should not need a Cloudflare Enterprise subscription.

**Decision.** Run production on the Workers Paid plan (from $5 a month per account plus usage). The Free plan's 10 ms CPU per request, 100,000 requests a day and missing Email Service sending rule it out for production. The only Enterprise-only feature in the earlier design, apex proxying for root domains, is dropped: sites use subdomains such as www, and owners redirect the root domain at their DNS provider.

**Consequences.** Predictable, low cost. Any future feature that needs Enterprise must be raised as a new decision.

## 009 — Staff sign-in with Better Auth over OIDC, not Cloudflare Access [#decision-009]

**Context.** Staff need SSO with the organization's identity provider. Cloudflare Access works at the network edge, which limits how much control Studio has over the sign-in experience and sessions.

**Decision.** Run our own auth with Better Auth in `studio-api`. Its `genericOAuth` plugin connects to the organization's one identity provider over OIDC, set in configuration ([Generic OAuth](https://better-auth.com/docs/plugins/generic-oauth)). Users, sessions and accounts live in D1 `core`. Previews open through Studio, which gives the preview host a short-lived signed token.

**Rejected.** SAML: its libraries are Node-only and unproven on Workers. Better Auth's SSO plugin: it loads those SAML libraries even for OIDC, and some of its features need transactions that D1 doesn't have.

**Consequences.** Full control over the sign-in experience and sessions, but we own the auth code path and its upgrades. The version is pinned at 1.7.6 or later, which includes the fixes for its 2026 security advisories.

## 008 — Agent on the Agents SDK, validated edits only, models chosen per task [#decision-008]

**Context.** The agent must be cheap to run, safe, and unable to damage live sites. The best model for each job will keep changing.

**Decision.** Each conversation is an `AIChatAgent` Durable Object from `@cloudflare/ai-chat` that acts as its owner. Its only write path is the same validated `applyOps` the editor uses, and it has no submit, publish, approve, settings or submissions tools. Models are chosen per task in configuration and called through AI Gateway, with per-brand spend limits. The default for routine edits is GLM-5.3 Flash on Workers AI.

**Rejected.** A fixed number of model tiers with automatic escalation; vector search over uploads; AI judges in the publish path; a second chat stack alongside the Agents SDK.

**Consequences.** Any model can be added or swapped without a code change. The eval suite runs whenever a task's model changes.

## 007 — One live, collaborative Durable Object per site, with edits by block ID [#decision-007]

**Context.** Several people, and their agents, may edit the same draft and page at the same time. Page locks would frustrate them.

**Decision.** A site's drafts live in one `SiteDoc` Durable Object built on PartyServer, Cloudflare's library from the PartyKit team for rooms, broadcast and hibernatable WebSockets ([cloudflare/partykit](https://github.com/cloudflare/partykit)). Every change goes through validated `applyOps`, with ops that address blocks by ID and field, never by position, and is broadcast live, with presence showing who is on which page, block and field. The server orders every batch. When two people change the same field, the later write wins and the other person is told. A rich text field is one value; presence marks who is typing in it.

**Rejected.** Page locks (too restrictive); drafts in D1 (no live ordering point); a CRDT for the whole document (it makes server-side validation hard); RFC 6902 JSON Patch (its array paths are positional, so a concurrent insert makes an op hit the wrong block); Yjs for rich text (a second sync system beside the ops, with its own undo, validation and history).

**Consequences.** Live collaboration with one rule. Two people can't type in the same paragraph with shared cursors; that isn't in this version. The same op vocabulary drives the editor, agent tools, undo and merging ([017](#decision-017)). The editor's behaviour under live remote changes is proven early in the [build plan](/build-plan#4-live-co-editing) (see [025](#decision-025)).

## 006 — Block versions: v1, v2, v3 for editors, any number live [#decision-006]

**Context.** [Decision 001](#decision-001) needs a concrete scheme that stays simple for editors.

**Decision.** Editors see versions as v1, v2, v3. Underneath, each released version has an opaque ID, and each draft's lockfile records those IDs. Released versions are frozen with no exceptions; any change to output is a new version, including urgent fixes, and the platform team can create upgrade drafts on every affected site. Any number of versions can be live at once. Studio encourages upgrades but never forces them. A version is kept while any draft or live release uses it, and for 3 months after the last one stops; the latest version of every block is always kept.

**Rejected.** A cap on live versions; major, minor and patch semantics with auto-applied patches; in-place fixes to released versions; keeping every version for as long as any retained release uses it.

**Consequences.** Upgrades are always a deliberate change through a draft and the site's workflow. Bundle size and visual-test time grow with the number of live versions, so CI tracks both. Rollback can't reach a release whose versions have been removed. Frozen versions still share primitives, Tailwind and React, so a dependency upgrade can change an old version's output; an intended change is accepted through a reviewed, audited screenshot update.

## 005 — Own the page schema; Puck edits it through an adapter [#decision-005]

**Context.** Every site is stored in the page format, so it must be stable and suited to agent edits. Puck's format is still evolving and nests blocks by position.

**Decision.** Our own schema (see [012](#decision-012)), with a flat block map in json-render's style, is canonical. Puck reads and writes it through a tested adapter. From json-render we borrow the catalog-to-prompt and streamed-patch ideas, not its renderer.

**Consequences.** One adapter to maintain. Content never depends on Puck, so the editor could be replaced. [Decision 025](#decision-025) did replace it: our own editor edits this schema directly, with no adapter.

## 004 — Publish immutable snapshots, render on request, cache per release [#decision-004]

**Context.** Live sites must never change by surprise, and publishing and rollback should be fast.

**Options.** (a) Pre-render every page to static HTML at publish. (b) Freeze content, theme and block versions in a snapshot and render on request, caching by release.

**Decision.** (b). A snapshot is a manifest plus one object per page, stored by content hash, so snapshots share unchanged pages and a render reads only the page it needs. Publishing and rollback are pointer changes: the site's Durable Object records the live release, and KV and D1 hold copies of it.

**Consequences.** No build pipeline and no archive of old assets. Shared code outside blocks can still affect live pages, so the visual regression gate covers it.

## 003 — Four Workers: a web and API pair for sites and for Studio [#decision-003]

**Context.** Public sites need to be fast and mostly static. Studio is a rich app. Separating web layers from API layers gives clean boundaries, matching the starter's pattern.

**Decision.** `sites` (Astro) renders public sites and previews, and forwards form posts to `sites-api`, which owns form intake and later payment webhooks. `studio` (TanStack Start with our [editor](/editor)) is the UI, and calls `studio-api` over RPC. `studio-api` owns domain logic, permissions, the Durable Objects and scheduled jobs. All four share packages.

**Rejected.** A single Worker per side (mixes UI and data access); separate Workers for rendering, the agent, forms and jobs (too many moving parts).

**Consequences.** Each UI talks to data only through its API. `sites-api` is small at first and grows when payments arrive.

## 002 — Host on Cloudflare [#decision-002]

**Context.** Pakshi needs global hosting, storage, AI access, custom domains and SSO for many sites.

**Decision.** Cloudflare: Workers, Durable Objects, D1, R2, KV, AI Gateway, the Agents SDK, Cloudflare for SaaS and Email Service.

**Consequences.** One platform covers almost every need. Email Service sending is in beta, which we accept. Snapshots are plain JSON, so content stays portable.

## 001 — Sites pin block versions [#decision-001]

**Context.** All sites render from one central block library. A major change to a block, such as a hero that renders differently on mobile, would reach every site at once. For some sites that change may not fit how they use the block.

**Options.** (a) Every site always uses the latest version of every block. (b) Each site depends on specific block versions and upgrades deliberately.

**Decision.** Option (b). Each site depends on specific block versions. The UI warns when a site is behind, and adopting an upgrade creates a draft that can be previewed.

**Consequences.** Live sites are never changed by surprise. The platform must keep old block versions working, and track and nudge sites that fall behind. The scheme is defined in [006](#decision-006).

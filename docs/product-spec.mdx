**What Pakshi does:** a non-technical team can launch and maintain a branded, multi-page site with a blog and a contact or registration form, on its own domain, with drafts, approvals and rollback, without a developer.

This doc defines what Pakshi does and for whom. It sits between the [vision](/vision) (why) and the [technical design](/technical-design) (how), and describes the product as it will be when the [build plan](/build-plan) is complete. **Guiding rule:** keep the product small and focused. Every feature must serve building or maintaining a good-looking branded site; anything else waits until real use asks for it.

## Roles and permissions

Pakshi has one permission system used everywhere. Studio, the API, the agent and live editing all ask the same question: may this person do this action on this thing?

- **Permissions** are fine-grained actions, such as edit pages, share drafts, publish a site, approve, approve changes you edited, edit a workflow, edit a brand theme, read submissions, export submissions, and manage members. Permissions decide what a person can do.
- **Roles** are named sets of permissions, for giving access quickly. Pakshi ships the default roles below, and admins can create custom roles.
- **Grants** give a person a role on the whole organization, on a brand (and all its sites), or on one site. A person can hold several grants.
- **Overrides** switch one permission on or off for one person on one scope. An override beats any role the person holds.
- **Delegation:** a person can grant only permissions they hold, on scopes they control.
- **Brands** are simply groupings of sites in Pakshi. What a brand represents is up to the organization.

- Studio only shows people what they're allowed to do.
- Org admins hold every permission, so they can grant any role, including Approver.

- The agent acts as its user and can do what they can, except submit and publish. A person always clicks Submit or Publish.
- The platform team holds org admin and ships blocks through the code repository, not through the app.

## Key journeys

Nine journeys cover the product. Each one reuses the same few building blocks: drafts, approvals and releases.

**1. Set up a brand** (org admin, brand admin)

1. The org admin creates the brand and assigns a brand admin.
2. The brand admin picks a theme preset and a brand color. Pakshi generates the full palette and blocks saving if text contrast fails WCAG AA.
3. They set fonts, density and other tokens, and upload the logo and favicon. Sites use the brand's theme and identity as they are.
4. They write the voice guide (tone, do and don't examples, words to avoid) and optionally set a brand approval workflow, which the brand's sites use unless they set their own.
5. Later changes to the theme, logo or favicon arrive on every site in the brand as a Brand update draft (journey 7).

**2. Launch a new site with the agent** (editor)

1. A brand admin creates the site and gives the editor access.
2. The editor starts a draft and describes the site to the agent: purpose, audience, pages, key dates, whether it needs a form. They attach source documents or images.
3. The agent proposes a site plan (pages, and the sections on each) based on the brand's recipes. The editor adjusts it in chat.
4. Once the plan is confirmed, the agent builds the pages section by section. The editor watches them appear on the canvas.
5. Where content is missing, the agent inserts a clearly marked placeholder rather than inventing facts. Pre-flight blocks submission while any remain.
6. If the agent needs something no block can do, it says so, suggests the nearest block, and offers to file a block request.
7. The editor shares the draft for feedback and submits it for approval (journey 4). A site admin connects a domain.

**3. Edit a page or write a blog post** (editor)

- **Drafts:** every change happens in a named draft, such as "Summer event launch" or "Fix the date". A site can have any number of drafts, and several people can edit one draft at once. A quick fix is a small draft.
- **Quick fix:** open a draft, click the text or image, change it. Changes save to the draft automatically; the live site is unchanged.
- **Bigger change:** ask the agent ("add a speakers section", "make this shorter"). If a section is selected on the canvas, the agent knows what "this" means. Each agent turn can be undone in one click.
- **Blog post:** create a post (title, excerpt, cover image, tags, author, body). The agent can draft it from notes.
- **Pages and navigation:** create, rename, unpublish and delete pages, and edit the menus, header and footer, all in a draft.

**4. Share and approve** (editor, approver)

1. Every draft has a preview link that shows its latest saved state. The editor shares the draft like a document: with named people, the whole organization, or anyone with the link, choosing view or edit access for each.
2. The editor submits the draft for approval. This freezes exactly what will be published.
3. The submission follows the applicable approval workflow. Each step's approvers are notified, open the preview, and see what changed compared with the live site.
4. When the last step approves, the draft publishes and is live within about a minute. With no steps, submitting publishes directly. Every other draft on the site is now behind (journey 5).
5. If an approver requests changes, the submission closes with their note and the editor resubmits when ready. Editing can continue during review; later edits aren't part of the submission under review.
6. If another draft publishes while this one is under review, the submission is updated automatically. A clean merge keeps its approvals. A merge that needed a person to resolve conflicts restarts the workflow.

**5. Update a draft that's behind** (editor)

1. When a draft publishes, every other draft on the site is behind. People already working in a draft can keep going. The next person to open it updates it, and it must be updated before it's submitted.
2. Pakshi merges the published changes into the draft, field by field. Changes to different fields, blocks or pages merge automatically, and so do identical changes made on both sides.
3. A conflict remains only where both sides changed the same field differently, one side edited a block the other removed, or both reordered the same existing sections. For each conflict, the editor keeps one side, or accepts a merge the agent suggests for a text field.

**6. Roll back** (editor)

Release history lists every publish with who submitted, who approved and when. **Roll back** undoes the most recent publish: the release that was live before it is live again within about a minute. It needs no approval, because that release was already approved and live. To bring back any older release, the editor restores it as a draft, which goes through the site's workflow like any other change. Drafts are untouched by a rollback, but they are now behind and update as in journey 5.

**7. Upgrade a block or take a brand update** (editor)

1. The site shows "Hero v2 available" with a short description of what changed.
2. **Adopt upgrade** creates a draft with the new version, converting content automatically where the block needs it.
3. The editor submits the draft like any other change. Nothing changes on the live site until it publishes.
4. The platform team can create upgrade drafts on every site that uses a block at once, for example after a security fix. Brand theme and identity changes arrive the same way, as a Brand update draft on each site. Each follows that site's workflow.

**8. Handle form submissions** (anyone with submissions access)

1. Open the site's submissions, pick a form, browse or search entries.
2. Export to CSV (audited), or delete everything for one person by email address.
3. Submissions are kept as part of the site's data for as long as the site exists.

**9. Request a new block** (editor)

Started from the agent or the block catalog. It files a request, with the need and an example, in the platform team's existing tracker. When the block ships, it appears in the catalog and the agent can use it.

## Feature requirements

These are the acceptance-level rules for the product, grouped by area.

### Editing

- All work happens in drafts. The agent and the visual editor change the same draft, and it saves automatically.
- Several people can edit the same draft and page at once. Everyone sees who else is there, which block and field they're on, and their changes as they happen, including the agent's. If two people change the same field, the later change wins and the other person is told.
- A text field someone is typing in shows as theirs to others and to the agent. This is a marker, not a lock.
- Every agent turn can be undone in one click. Undo leaves alone any field someone else has changed since, and says so. Each editing session and agent turn is kept in the draft's history.
- Every change is checked against the block's rules before it's saved.

### Drafts and merging

- A site can have any number of named drafts. Each draft starts from a release. Publishing a draft closes it, unless someone edited it after it was submitted. Then it stays open with those edits, based on the release it just published.
- When a draft publishes, every other draft on the site is behind. People already working in a draft keep going. A draft that's behind must be updated the next time someone opens it, and before it's submitted.
- Updating merges field by field against the release the draft started from. Identical changes on both sides aren't conflicts, and sections added on both sides are all kept. Only real conflicts need a person: the same field changed differently on both sides, a block edited on one side and removed on the other, or the same existing sections reordered on both sides. The agent may suggest a merge for a text field; a person accepts it or picks a side.
- If the two sides use different versions of a block, both are brought to the newer version before merging. The merged draft is then checked for structure (block rules and references), and anything that fails is shown as a conflict, so a merge never produces a broken page. Pre-flight checks, such as no placeholders left, run only at submission.

### Pages, menus, header and footer

- Each site has one header and one footer. Each is a block chosen from the header or footer block types, with variants, and is versioned like any other block.
- Each site has two menus: main and footer. A menu is an ordered list of items, each a label and a link to a page on the site or to an external address. The main menu can nest one level deep. The header shows the main menu and the footer shows the footer menu.
- A menu link to a page follows it when the page's address changes. Unpublishing or deleting a page removes it from the menus in the same draft, and Pakshi says so.
- **Unpublishing** a page marks it as unpublished in the draft. When the draft publishes, the page leaves the live site, the sitemap and the menus, and its address returns "gone" (HTTP 410) unless the editor adds a redirect, which Pakshi offers when unpublishing. The page stays in the draft and can be published again.
- **Deleting** a page has the same effect on the live site, and also removes the page from the draft.

### Sharing and previews

- Drafts are shared like documents: with named people, the whole organization, or anyone with the link. The person sharing chooses view or edit access for each.
- Editing always needs a signed-in Pakshi user. A link shared for editing gives signed-in users edit access and everyone else view access.
- Edit access through a share covers that draft only. It never includes submitting or publishing.
- Every draft has a preview link, at an address that can't be guessed, showing the draft's latest saved state. Who can open it follows the draft's sharing. Sharing can be revoked at any time.
- Previews are never indexed by search engines, and forms in previews don't submit. A preview lives as long as its draft.

### Approvals and publishing

- Workflows can be set on the organization, a brand or a site, and the nearest one applies. A workflow is an ordered list of any number of steps, including none. Each step names who can approve (roles or specific people) and how many approvals it needs.
- Editing a workflow is a permission. The workflow editor is a simple list of steps.
- An approver needs the approve permission on that site. Approving a change you edited needs the separate permission for it.
- Submitting freezes the draft exactly as it will be published. Approvals apply to that frozen version only. Submitting the same draft again replaces its pending submission and restarts the workflow.
- If another draft publishes during review, the submission is updated automatically. A clean merge keeps its approvals; a merge that needed conflict resolution restarts the workflow.
- A submission publishes only if it's based on the current live release, so a final approval can never overwrite a release that went live during review.
- Pre-flight must pass before submitting: no placeholders left, alt text on every meaningful image, page title and description set, no broken internal links, form notification address set.
- A publish is live worldwide within about a minute. Every release is kept.
- Rollback without approval undoes only the most recent publish, and takes about a minute. An older release comes back only as a draft, through the site's workflow, and only while its block versions and media are still kept.

### Blocks and versions

- Each site stays on the block versions it uses until an editor adopts an upgrade, through a draft and the site's workflow.
- Any change that alters how a block looks creates a new version, shown to editors as v1, v2, v3 and so on. Any number of versions can be live at once. Sites on an older version see a banner encouraging them to upgrade, but are never forced.
- An urgent fix is a new version like any other. The platform team can create upgrade drafts on every affected site at once.
- A block version is kept while any draft or live release uses it, and for 3 months after the last one stops. The latest version of every block is always kept.
- The library covers at least these page sections: hero, rich text, split, feature grid, call to action, gallery, form, blog list, header and footer, and grows to about 20 blocks and 4 recipes (landing, event, information site, blog), chosen from the sites Pakshi's first users build.

### Brands and themes

- Theme tokens: brand color (full palette generated from it), neutral tone, fonts, type scale, corner radius, density, shadow style, section backgrounds, image corners, motion on or off. Every theme has a light and a dark mode, both contrast-checked. Sites follow the visitor's system setting, with an optional toggle.
- Sites use their brand's theme and identity as they are. There are no site theme overrides and no brand locks.
- Each save of a brand's theme, logo or favicon is a new brand revision. Each draft records the brand revision it uses, the way it records block versions, so other drafts never pick up a brand change.
- A new brand revision creates a Brand update draft on every site in the brand, which follows that site's workflow. If a site already has an unpublished Brand update draft, it moves to the newer revision instead of a second draft being created.

### Sites and brands

- Org and brand admins create sites. Every site gets a platform subdomain immediately.
- Deleting a site needs its name typed to confirm, and offers a submissions export first. The site stops serving at once and its custom domains are released. Its drafts, releases, submissions, media and history are kept for 30 days, during which an org admin can restore the site, and are then deleted for good. Every deletion and restore is audited.
- A brand can be deleted only once it has no sites.

### Forms and submissions

- Field types: short text, long text, email, phone, select, checkbox (for consent), hidden (for tracking codes).
- Editors create and edit forms in a draft. Notification addresses are site settings. Each submission keeps the field labels it was sent with, so exports still read correctly after a form changes.
- A consent checkbox and privacy link are required when a form collects personal data.
- Each form sends a notification email to its configured addresses. Forms send no email to submitters.
- There is no spam protection. Form posts over 64 KB are rejected.
- Each site's submissions are stored in their own database, separate from every other site's, so a flood of submissions on one site can't affect another.
- Submissions are kept for as long as the site exists, as part of its data. A single submission, or everything for one person, can be deleted on request. Every view, export and deletion is logged. The agent never has access to submissions.

### Email

Transactional only: form notifications and Studio notifications. Sent from a shared default sender, or from a brand or site sender domain that uses Cloudflare DNS.

### Media

Each brand has a library (logos, approved images) that its sites can use; each site has its own. Images are resized and optimized automatically. Alt text is required: the agent suggests it and a person confirms. Files never change: each upload is a new file with its own ID, so a new image replaces an old one only where someone swaps it in. The brand's logo and favicon are brand settings, so changing them reaches every site through a Brand update draft. A file is kept while any draft or live release uses it, and for 3 months after the last one stops.

### SEO and domains

- Per page: title, description, social image (defaults to the page's hero image or the brand default), canonical URL and a no-index option. Automatic sitemap, robots.txt and blog RSS feed. Changing a page's address offers to add a redirect.
- Custom subdomains are added with guided DNS steps and automatic HTTPS. Root domains (example.org without www) aren't supported directly: sites use a subdomain such as www, and the root redirects to it.

### Accessibility

Every block version meets WCAG 2.2 AA before release. Pre-flight checks heading order, alt text, link text and form labels. Studio itself targets WCAG 2.2 AA.

## Non-goals

- Not a free-form website builder: no custom layouts, CSS, code, HTML embeds or third-party scripts from editors.
- No plugins or tenant code. Blocks come only from the platform team.
- Not a headless CMS: no public content API.
- No e-commerce, memberships or site visitor logins.
- No marketing email, newsletters or CRM.
- Not a digital asset management system: the media library serves websites only.
- The agent never writes code, never submits or publishes, and never sees form submissions.
- No approvers outside Pakshi. Anyone can view a draft shared by link, but only Pakshi users approve.
- No page locks. People edit together, with presence showing who is where.
- No media file versions. Files never change; a new file is a new upload.
- No choosing an older brand theme. Sites move forward through Brand update drafts.

## Success metrics

These measure whether Pakshi works once people use it for real sites.

| Metric                | Definition                                                           | Target                   |
| --------------------- | -------------------------------------------------------------------- | ------------------------ |
| Time to launch        | Site created → first publish (median)                                | 10 business days or less |
| Time to change        | Draft created → submitted (median)                                   | 15 minutes or less       |
| Block requests        | Block requests filed per active site per month                       | Falling month over month |
| Approval turnaround   | Submit → final decision (median)                                     | 1 business day or less   |
| Agent success         | Agent turns not undone                                               | 75% or more              |
| Untracked changes     | Live changes not traceable to a publish or rollback in the audit log | 0                        |
| Agent cost per launch | Model cost from site created → first publish (median)                | Tracked; no target yet   |

## Settled context

- Pakshi is open source. The team building it is its first user.
- Data residency is not a constraint.
- The platform team curates which AI models are used, and all providers are approved. Users never choose models.
- Brands are groupings of sites; access is controlled entirely by roles and permissions.
- Approval requirements are whatever the applicable workflow defines, and a workflow can have no steps.
- All approvers are Pakshi users. Drafts can be shared for viewing with anyone through a link.
- Blocks are designed and built by the platform team.
- Cloudflare Email Service sends all email.

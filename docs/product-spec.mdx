**The MVP:** a non-technical team can launch and maintain a branded, multi-page site with a blog and a contact or registration form, on its own domain, with previews, approvals and rollback, without a developer.

This doc defines what Pakshi does and for whom. It sits between the [vision](/vision) (why) and the [technical design](/technical-design) (how). **Guiding rule:** keep the product small and focused. Every feature must serve building or maintaining a good-looking branded site; anything else waits until a pilot asks for it.

## Roles and permissions

Pakshi has one permission system used everywhere. Studio, the API, the agent and live editing all ask the same question: may this person do this action on this thing?

- **Permissions** are specific actions, such as edit pages, publish a site, approve, edit a workflow, edit a brand theme, read submissions, export submissions, and manage members.
- **Roles** are named sets of permissions. Pakshi ships the default roles below, and admins can create custom roles.
- **Grants** give a person a role on the whole organization, on a brand (and all its sites), or on one site. A person can hold several grants.
- **Brands** are simply groupings of sites in Pakshi. What a brand represents is up to the organization.

## Key journeys

Eight journeys cover the MVP. Each one reuses the same few building blocks: the draft, previews, approvals and releases.

**1. Set up a brand** (org admin, brand admin)

1. The org admin creates the brand and assigns a brand admin.
2. The brand admin picks a theme preset and a brand color. Pakshi generates the full palette and blocks saving if text contrast fails WCAG AA.
3. They set fonts, density and other tokens, then choose which token groups are locked for sites. Colors, fonts and logo are locked by default.
4. They write the voice guide (tone, do and don't examples, words to avoid) and set a default approval workflow for the brand's sites.

**2. Launch a new site with the agent** (editor)

1. The editor creates a site and describes it to the agent: purpose, audience, pages, key dates, whether it needs a form. They attach source documents or images.
2. The agent proposes a site plan (pages, and the sections on each) based on the brand's recipes. The editor adjusts it in chat.
3. Once the plan is confirmed, the agent builds the pages section by section. The editor watches them appear on the canvas.
4. Where content is missing, the agent inserts a clearly marked placeholder rather than inventing facts. Pre-flight blocks submission while any remain.
5. If the agent needs something no block can do, it says so, suggests the nearest block, and offers to file a block request.
6. The editor previews, submits for approval (journey 4), and connects a domain.

**3. Edit a page or write a blog post** (editor)

- **Quick fix:** open the page, click the text or image, change it. Changes save to the draft automatically; the live site is unchanged.
- **Bigger change:** ask the agent ("add a speakers section", "make this shorter"). If a section is selected on the canvas, the agent knows what "this" means. Each agent turn can be undone in one click.
- **Blog post:** create a post (title, excerpt, cover image, tags, author, body). The agent can draft it from notes.

**4. Preview and approve** (editor, approver)

1. The editor creates a preview of the current draft (one page or the whole site). It gets its own link, is visible to signed-in Pakshi users, and expires after 7 days by default.
2. The editor submits for approval. This freezes exactly what will be published.
3. The submission follows the site's approval workflow. Each step's approvers are notified, open the preview, and see what changed compared with the live site.
4. When the last step approves, the site publishes and is live within about a minute. A site whose workflow has no steps publishes directly.
5. If an approver requests changes, the submission closes with their note and the editor resubmits when ready. Editing can continue during review; later edits aren't part of the submission under review.

**5. Roll back** (editor)

Release history lists every publish with who submitted, who approved and when. **Roll back** makes an earlier release live again within about a minute. It needs no approval, because that release was already approved. The draft is untouched.

**6. Upgrade a block** (editor)

1. The site shows "Hero v2 available" with a short description of what changed.
2. **Preview upgrade** creates a preview with the new version, converting content automatically where the block needs it.
3. The editor submits the upgrade like any other change. Nothing changes on the live site until it's approved.

**7. Handle form submissions** (anyone with submissions access)

1. Open the site's submissions, pick a form, browse or search entries.
2. Export to CSV (audited), or delete everything for one person by email address.
3. Submissions are kept as part of the site's data for as long as the site exists.

**8. Request a new block** (editor)

Started from the agent or the block catalog. It files a request, with the need and an example, in the platform team's existing tracker. When the block ships, it appears in the catalog and the agent can use it.

## Feature requirements

These are the acceptance-level rules for the MVP, grouped by area.

**Editing**

- The agent and the visual editor change the same page. There is one draft per site, and it saves automatically.
- Several people can edit the same site and page at once. Everyone sees who else is there, which block they're on, and their changes as they happen, including the agent's. Two people can type in the same text at once and see each other's cursors. For other settings, if two people change the same one, the later change wins.
- Every agent turn can be undone in one click. Each editing session and agent turn is kept in the page's history.
- Every change is checked against the block's rules and the brand's locks before it's saved. Locked options aren't shown as editable, and the agent refuses them with an explanation.

**Previews**

- A preview is a frozen copy of the draft (one page or the whole site) at its own link.
- Visible to signed-in staff only. Default lifetime 7 days, maximum 30. Previews are never indexed by search engines, and forms in previews don't submit.

**Approvals and publishing**

- Each site has an approval workflow, defaulting to its brand's. A workflow is an ordered list of any number of steps. Each step names who can approve (roles or specific people) and how many approvals it needs.
- Brand and site admins edit workflows in Studio. The MVP editor is a simple list of steps. A visual, node-based editor for drawing steps and arrows is on the Later list, and can be pulled forward cheaply with an off-the-shelf flow library.
- Submitting freezes exactly what will be published. Approvals apply to that frozen version only. Submitting again replaces the pending submission and restarts the workflow.
- Pre-flight must pass before submitting: no placeholders left, alt text on every meaningful image, page title and description set, no broken internal links, form notification address set.
- A publish is live worldwide within about a minute. Every release is kept, and rolling back to any of them also takes about a minute.

**Blocks and versions**

- Each site stays on the block versions it uses until an editor adopts an upgrade, through preview and approval.
- Any change that alters how a block looks creates a new version, shown to editors as v1, v2, v3 and so on. Any number of versions can be live at once. Sites on an older version see a banner encouraging them to upgrade, but are never forced.
- The only exception to "no surprises" is an urgent security or accessibility fix, which the platform team may apply to an existing version. This is audited and site admins are notified.

**Brands and themes**

- Theme tokens: brand color (full palette generated from it), neutral tone, fonts, type scale, corner radius, density, shadow style, section backgrounds, image corners, motion on or off. Every theme has a light and a dark mode, both contrast-checked. Sites follow the visitor's system setting, with an optional toggle.
- Theme changes appear in every site's draft right away and reach each live site with its next approved publish.

**Forms and submissions**

- Field types: short text, long text, email, phone, select, checkbox (for consent), hidden (for tracking codes).
- Spam protection on every form: Turnstile, a hidden honeypot field and rate limits. A consent checkbox and privacy link are required when a form collects personal data.
- Each form sends a notification email to its configured addresses and can send the submitter a branded confirmation.
- Submissions are kept for as long as the site exists, as part of its data. A single submission, or everything for one person, can be deleted on request. Every view, export and deletion is logged. The agent never has access to submissions.

**Email**

Transactional only: form notifications, confirmations and Studio notifications. Sent from a verified brand or site sender domain, or from a shared default sender.

**Media**

Each brand has a library (logos, approved images) that its sites can use; each site has its own. Images are resized and optimized automatically. Alt text is required: the agent suggests it and a person confirms. Replacing a file updates it everywhere it's used.

**SEO and domains**

- Per page: title, description, social image (defaults to the page's hero image or the brand default), canonical URL and a no-index option. Automatic sitemap, robots.txt and blog RSS feed. Changing a page's address offers to add a redirect.
- Every site gets a platform subdomain immediately. Custom subdomains are added with guided DNS steps and automatic HTTPS. Root domains (example.org without www) aren't supported directly: sites use a subdomain such as www, and the root redirects to it.

**Accessibility**

Every block version meets WCAG 2.2 AA before release. Pre-flight checks heading order, alt text, link text and form labels. Studio itself targets WCAG 2.2 AA.

## Non-goals

- Not a free-form website builder: no custom layouts, CSS, code, HTML embeds or third-party scripts from editors.
- No plugins or tenant code. Blocks come only from the platform team.
- Not a headless CMS: no public content API.
- No e-commerce, memberships or site visitor logins.
- No marketing email, newsletters or CRM.
- Not a digital asset management system: the media library serves websites only.
- The agent never writes code, never publishes, and never sees form submissions.

## Success metrics

| Metric                 | Definition                                           | Pilot target             |
| ---------------------- | ---------------------------------------------------- | ------------------------ |
| Time to launch         | Site created → first publish (median)                | 10 business days or less |
| Time to change         | Change requested → ready for approval (median)       | 15 minutes or less       |
| Developer-free changes | Share of publishes with no platform team involvement | 80% or more              |
| Approval turnaround    | Submit → final decision (median)                     | 1 business day or less   |
| Agent success          | Agent turns kept without undo or manual rework       | 75% or more              |
| Surprise changes       | Live sites changed without an approved publish       | 0                        |

## Settled context

- Data residency is not a constraint.
- The platform team curates which AI models are used, and all providers are approved. Users never choose models.
- Brands are groupings of sites; access is controlled entirely by roles and permissions.
- Approval requirements are whatever each site's workflow defines.
- All reviewers are Pakshi users; there are no outside reviewers.
- Blocks are designed and built by the platform team.
- Cloudflare Email Service sends all email.

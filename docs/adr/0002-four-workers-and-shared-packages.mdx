Pakshi replaces the starter's sample app with this layout:

```text
apps/studio                      TanStack Start admin app (the starter's apps/web)
apps/sites                       Astro app that serves every site and preview
workers/studio-api               Plain Worker: sign-in, domain logic, SiteDoc, SiteAgent
workers/sites-api                Plain Worker: form intake, SiteSubmissions
workers/test-identity-provider   OIDC provider for non-production stages
packages/contracts               Page document, snapshot manifest, KV routing values
packages/domain                  authorize, the permission catalogue and default roles
packages/blocks                  Field builders, field components, registry, block versions
packages/tokens                  Resolved theme schema, presets, CSS output
packages/ui                      shadcn/ui components for Studio and the editor
packages/editor                  @repo/editor, the visual editor Studio edits drafts with
packages/agent                   The agent's tools, prompts, turns and eval suite
packages/brand                   Pakshi's own logos, marks and icons
fixtures/sample-site             The hand-written snapshot non-production stages serve
```

`studio-api` and `sites-api` are plain Workers with their own entry files, because PartyServer's Durable Objects are plain classes. Their Durable Object classes are exported from the entry file and declared in the Worker's `env`.

`infra/src/worker-bindings.ts` defines every Worker's bindings and exports its env type, which each runtime imports from `@repo/infra/worker-bindings`. The infra package reaches Worker source through relative imports, never package dependencies, so no package depends on infra and infra on it in turn.

The test identity provider deploys to every stage except production. Anyone who can reach it can sign in as a test user, so non-production stages hold only test data.

This plan builds the product described in the [product spec](/product-spec) and the [technical design](/technical-design), one checkpoint at a time. When every checkpoint is done, Pakshi is complete.

## How to use this plan

- **Build the checkpoints in order.** Each one starts from the finished state of the one before it.
- **The spec and the design are the source of truth.** A checkpoint lists what to build and links to the sections that define it; it doesn't restate them. If building something shows the design is wrong, change the design doc and record the decision in the [decision log](/decision-log).
- **A checkpoint is done when its checks pass.** Each check is a test, automated wherever possible, and every earlier checkpoint's tests keep passing.
- **Every checkpoint ends in a demo** someone can run locally with `pnpm dev`. Checks that need Cloudflare's network, such as custom hostnames or KV propagation, run against production.
- **The riskiest work comes first.** Checkpoints 1 to 5 prove the [unproven assumptions](/technical-design#unproven-assumptions) before much depends on them.
- **Studio screens follow the [Studio designs](https://claude.ai/artifact/Soz1iX7Fw3M1KnotJgL5QU)**, built as each checkpoint needs them.
- **This doc changes as we learn.** Tick checkpoints off, and split or reorder them when that makes the work clearer.

## 1. Skeleton

Turn the starter into Pakshi's four Workers and prove that everything deploys together.

**Build:**

- Remove the starter's sample CSV app, and make [destroying a stack](/technical-design#repository-and-environments) delete everything in it. Update `AGENTS.md` and `apps/web/AGENTS.md`, and record the new layout in an ADR.
- The [repository layout](/technical-design#repository-and-environments): `sites` (Astro 7), `sites-api`, `studio` (from `apps/web`) and `studio-api` as a plain Worker, all in the Alchemy graph. Declare the `SiteDoc`, `SiteAgent` and `SiteSubmissions` Durable Object classes, even if they do little yet.
- D1 `core` with users and sessions, and [staff sign-in](/technical-design#security-and-access) through Better Auth's `genericOAuth` against a test OIDC provider.
- `authorize` with the permission catalogue and the [default roles](/product-spec#roles-and-permissions), seeded for test users. There's no permissions UI yet.
- The [page document](/technical-design#the-page-document) schema and the snapshot manifest format in `packages/contracts`.
- `packages/blocks` with the field builders, the [field components](/editor#with-blocks) blocks render their fields through, the generated registry, and three blocks (hero, rich text, call to action) with fixtures. `packages/tokens` with one theme preset in light and dark.
- `sites` [serving](/technical-design#publishing-serving-and-previews) a hand-written snapshot from R2 through the KV `host → site → release` lookup, with the release and Worker version in the cache key.

**Demo:** sign in to Studio in the dev stack, then open the Sites address, which serves a page from the hand-written snapshot, in light and dark.

**Done when:**

- `pnpm dev` runs all four Workers and the three Durable Object classes locally.
- A test user signs in through the test OIDC provider in the dev stack.
- The served page matches its fixture screenshot in light and dark, and a second request is a cache hit.
- `authorize` has tests for every default role on organization, brand and site scopes.

**Proves:** hosting in Alchemy.

## 2. Editing content

One person edits the content of a page in Studio, and the editor and the published site render the same.

**Build:**

- [`SiteDoc`](/technical-design#editing-the-site-document-and-the-editor), stored one row per page, with one draft per site until checkpoint 5 adds named drafts: `applyOps` with ops addressed by block ID, batch IDs, validation with completeness left to freezing, and history.
- The document module in `packages/domain` (`applyOps`, validation and inverse ops), importable in the browser.
- The site-level parts of the [page document](/technical-design#the-page-document): header and footer blocks, and the menus data. Menus get their editing screen in checkpoint 9.
- [`@repo/editor`](/editor) for one person: the canvas, the local copy of the draft with its pending batches, selection and overlays, plain text and rich text edited in place, the media popover, the settings panel, undo per command, and the field kinds and commands they're built from.
- The Studio editor screen (canvas and settings panel) and the page list: create, rename and open pages and posts.
- The rest of the core blocks: split, feature grid, gallery, form (display only), blog list, header and footer, each with fixtures.
- The [quality gates](/technical-design#blocks-and-versioning): screenshots of every fixture in the editor canvas and in `sites`, axe checks, and the lint rule against literal colors, fonts and spacing.

**Demo:** edit text, rich text and images on a page in Studio, reload, and undo.

**Done when:**

- Every fixture's screenshot matches between the editor canvas and `sites`, in light and dark.
- An edit survives a reload, and undo reverses one action at a time.
- A required heading can be cleared and retyped, and a heading over its maximum length is refused while typing.
- `applyOps` rejects invalid batches with structured errors, with a test for each validation rule.
- Every field in the core blocks can be reached and edited with the keyboard alone.
- The editor meets its [performance budgets](/editor#performance-budgets).

**Proves:** render parity.

## 3. Editing structure

One person adds, moves and removes sections and items, with a pointer or with the keyboard alone.

**Build:**

- [Insert points and the block picker](/editor#structure), offering only the blocks each spot allows, with placeholder content for new blocks.
- Moving blocks by drag in the canvas and in the outline panel, and the move commands, with screen reader announcements.
- Duplicating and removing blocks, and choosing variants and surfaces from previews.
- The outline panel.
- [Commands](/editor#extension-points) as one definition each, with their shortcut, menu and toolbar entries, and availability check. Undo, redo and the block navigation from checkpoint 2 move onto them.

**Demo:** build a page from an empty draft by adding, reordering and removing sections and items, once with a mouse and once with the keyboard only.

**Done when:**

- Every structural change can be made with the keyboard alone, and each one is announced.
- A drag and the matching move command produce the same ops.
- The picker never offers a block the spot doesn't allow, such as an interactive block inside a section.
- Undo reverses an insert, a move, a duplicate and a removal.
- axe finds no violations on the editor screen.

## 4. Live co-editing

Several people and their presence in one draft, and no one loses their place when someone else edits.

**Build:**

- PartySocket connections from Studio to `SiteDoc` through `studio-api`, with the WebSocket passed over the service binding.
- [Live collaboration](/technical-design#editing-the-site-document-and-the-editor): broadcast, presence per draft, page, block and field, confirmation by batch ID and resending after a reconnect, later write wins with a notice, dropped ops on removed blocks with a notice, the typing marker, and the per-connection permission cache.
- In the editor: pending batches replayed over each broadcast, other people's presence on the canvas, and the [rules for remote changes](/editor#remote-changes).

**Demo:** two browsers edit the same page in the dev stack, each seeing the other's presence and changes live.

**Done when:**

- A convergence test, with simulated clients making random concurrent edits against the real document module, ends with every client showing the server's document.
- In a scripted two-browser session on one draft, every change is either applied or its author is told.
- Each rule for remote changes has a browser test that fails without it.
- Undo in one browser never removes the other person's edits.

The check that removing a person's permission stops their next batch moved to checkpoint 10, which adds the grant changes that cause it ([decision 041](/decision-log#decision-041)).

**Proves:** live co-editing in the editor.

## 5. Publishing and merging

Named drafts that publish, roll back, and merge like branches. Every workflow has no steps until checkpoint 6, so submitting publishes directly.

**Build:**

- [Named drafts](/product-spec#drafts-and-merging): the drafts list, each draft's base release, the behind state, and closing drafts.
- [Snapshots](/technical-design#publishing-serving-and-previews): the manifest and content-addressed page objects, and freezing with structure checks.
- Publishing through `SiteDoc`: the release recorded as the source of truth, the KV write, the outbox to D1, and the reconcile job.
- Rollback of the latest publish, and restoring an older release as a draft.
- The [three-way merge](/technical-design#publishing-serving-and-previews), with block versions migrated before diffing, and the conflict screen with pick-a-side. Model suggestions for text conflicts come in checkpoint 7.

**Demo:** two people work in two drafts; one publishes; the other opens their draft, updates it, resolves a conflict, and publishes; then someone rolls back.

**Done when:**

- Scripted merge cases produce the expected valid result for every conflict type, the non-conflicts (identical changes, additions on both sides), site-level parts, and sides on different block versions.
- Two publishes started at once on one site happen one after the other.
- The reconcile job restores a KV entry that was changed by hand.
- A draft edited after it was submitted stays open after publishing, and keeps only its later edits.

The checks that a publish and a rollback are live on a production platform subdomain within 60 seconds, and that no cached page links to CSS or JavaScript a `sites` deploy removed, moved to checkpoint 9, which builds domains and needs production ([decision 052](/decision-log#decision-052)).

**Proves:** the three-way merge.

## 6. Approvals, sharing and previews

Changes reach production through the workflows owners set, and drafts are shared like documents.

**Build:**

- [Approval workflows](/product-spec#approvals-and-publishing) on the organization, a brand or a site, and the workflow editor as a list of steps.
- Submissions and approval progress in `SiteDoc`, with the D1 copy, stale-approval rejection, and the release turn that orders them with publishing ([decision 057](/decision-log#decision-057)).
- [Pre-flight](/product-spec#approvals-and-publishing) at submission. Its check for a form notification address comes with forms in checkpoint 9, which adds the setting.
- The Approvals screen with the preview and what changed, and approval notifications through Email Service.
- [Sharing](/product-spec#sharing-and-previews) with people, the organization or anyone with the link, with view or edit access, stored with the draft in `SiteDoc` ([decision 055](/decision-log#decision-055)).
- [Previews](/technical-design#publishing-serving-and-previews) served by Studio, which checks the draft's sharing on every request ([decision 054](/decision-log#decision-054)), with screenshot checks against `sites`.

**Demo:** an editor shares a draft by link, submits it, and it goes through a two-step workflow to live; meanwhile another draft publishes and the submission updates itself.

**Done when:**

- When two final approvals race, exactly one release goes live.
- A decision made on a submission that changed since it was loaded is rejected.
- A clean merge during review keeps the approvals, and a merge that needed a person restarts the workflow.
- Pre-flight blocks a submission while a placeholder remains.
- A preview opens for someone it's shared with and not for anyone else, and revoking access blocks the next request.
- Previews send no-index headers, and their forms don't submit.

## 7. The agent

The agent builds and edits sites through the same path as people.

**Build:**

- [`SiteAgent`](/technical-design#the-agent) on PartyServer and Effect AI, one per person and draft, reached only through `studio-api`'s agent route with the trusted user header ([decision 058](/decision-log#decision-058), [decision 061](/decision-log#decision-061)).
- The chat panel through `studio-api`: it catches up on the conversation when it connects and follows each turn as it streams.
- In the editor: [the agent's changes highlighted](/editor#with-the-agent) as they land, the selected block passed to the agent, and undo of an agent turn from the chat panel.
- Every agent tool, including `propose_plan` ([decision 060](/decision-log#decision-060)), the recipes `get_recipe` and `create_page` read, the cacheable context prefix, structured validation errors with two repair attempts, and presence as the agent acting for its user.
- Source uploads with `toMarkdown`, `fetch_url` with its limits, alt text suggestions, and merge suggestions for text conflicts.
- AI Gateway with cost tags and one spend limit for the product ([decision 059](/decision-log#decision-059)).
- The eval suite, run on demand when prompts, models or block contracts change ([decision 062](/decision-log#decision-062)).

**Demo:** describe a small site in chat, confirm the plan, and watch the agent build it section by section while another person watches the same draft.

**Done when:**

- GLM-5.3 Flash completes 8 of 10 scripted edits with the expected result, with tool calls streamed through AI Gateway.
- The eval suite passes, with no successful prompt injection.
- A request routed at `SiteDoc` through the agent route is refused, and so is a client-sent trusted header.
- The agent can't submit or publish, and can't reach submissions.
- When AI Gateway refuses a request because the spend limit is reached, the person gets a clear message.

**Proves:** the agent on a cheap model, and the chat path.

## 8. Brands, themes and block versions

Brands own their look, and blocks improve without surprising live sites.

**Build:**

- [Theme Studio](/product-spec#brands-and-themes): presets, palette generation, contrast checks in light and dark, fonts served by each app, identity and the voice guide.
- [Brand revisions](/technical-design#themes) pinned per draft, and Brand update drafts.
- [Block versioning](/technical-design#blocks-and-versioning): the lockfile of version numbers, `migrate` chains, adopting an upgrade, upgrade drafts on every affected site, retention, the frozen-folder CI check, golden JSON Schema tests, and the reviewed screenshot-update path.
- The library grows to about 20 blocks and 4 recipes, chosen from the sites the Pakshi team plans to build.

**Demo:** change a brand's color and watch Brand update drafts appear on its sites; release a block's v2 and upgrade one site to it through a draft.

**Done when:**

- Two versions of one block are live at once, on two sites the `sites` Worker serves, with its startup measured well under 1 second. A lockfile pins one version of each block, so one site can't show two.
- A theme with a failing contrast pair can't be saved.
- A brand change reaches a site's live pages only when its Brand update draft publishes.
- An upgrade from v1 to v3 migrates content through both steps.
- CI rejects an edit to a released block's folder.

**Proves:** block versions at runtime.

## 9. Site essentials

Everything else a real site needs.

**Build:**

- [Forms and submissions](/product-spec#forms-and-submissions): the form editor, intake into `SiteSubmissions` with the 64 KB cap, notification emails with retry, pre-flight's check for a notification address, the submissions screen, CSV export and deletion by email.
- The [media library](/product-spec#media): brand and site libraries, uploads from the library and from the editor's media popover, Cloudflare Images, alt text, and retention.
- [Pages, menus, header and footer](/product-spec#pages-menus-header-and-footer): the menus screen, unpublishing and deleting pages, and 410 for removed addresses.
- [SEO](/product-spec#seo-and-domains): page metadata, sitemap, robots.txt, the blog RSS feed and redirects.
- [Custom domains](/technical-design#domains) through Cloudflare for SaaS, with the TXT ownership check, and every site's platform subdomain in production. Serving from a custom domain is also what turns on the page cache ([decision 027](/decision-log#decision-027)).
- [Deleting sites and brands](/product-spec#sites-and-brands), with the 30-day restore window.

**Demo:** build a site with a registration form on a custom subdomain, submit the form, see the notification, and export the submission.

**Done when:**

- A form post lands only in that site's `SiteSubmissions` and sends its notification.
- Flooding one site's form leaves another site's forms working.
- A custom hostname serves over HTTPS in production.
- A publish and a rollback are each live on a production platform subdomain within 60 seconds.
- After a `sites` deploy, no cached page links to CSS or JavaScript the deploy removed.
- An unpublished page returns 410 and leaves the sitemap and menus.
- A deleted site stops serving at once, and an org admin can restore it within 30 days.

## 10. Ready for real sites

Finish access control, safety and operations, then run real sites on Pakshi.

**Build:**

- The [permissions](/product-spec#roles-and-permissions) screens: members, grants, custom roles, overrides and the delegation rule. Each change tells the `SiteDoc`s it affects to reload the permissions their live connections hold ([decision 041](/decision-log#decision-041)).
- The audit log's viewer, with every audited action recorded.
- Pre-flight's [accessibility checks](/product-spec#accessibility), and Studio at WCAG 2.2 AA.
- The content security policy on every site.
- [Operations](/technical-design#operations): alerts, and the restore drill in production.
- Block requests filed into the platform team's tracker.
- Recording for every [success metric](/product-spec#success-metrics).

**Demo:** the Pakshi team launches its first real site on a custom domain, using only Studio and the agent.

**Done when:**

- Delegation tests show no one can grant a permission they don't hold or a scope they don't control.
- Removing a person's permission stops their next batch.
- The restore drill has been run, and its steps are written down.
- A security review has passed.
- Every success metric is being recorded.
- The first real site is live, and every change to it went through Pakshi.

## After the last checkpoint

Pakshi is complete. The Pakshi team runs its sites on it and watches the [success metrics](/product-spec#success-metrics). Anything from the spec's "Not in this version" list is added only when real use asks for it, through the spec, the design and a new plan.
